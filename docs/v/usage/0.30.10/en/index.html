Usage 0.30.10

Released: 2026-09-07

Release notes

FEATURE

Grok arrives in usage reports and the interactive dashboard with four synchronized lookup tables

Developers who regularly collaborate with Grok can now finally include its usage in statistics when running usage report or switching to the interactive dashboard.

This is like a mall information desk displaying membership cards for a new boutique while the floor directory and register rosters omit it entirely, leaving shoppers unable to find it on the mall-wide directory until lookup tables everywhere are completed.

While the macOS menu bar previously had a Grok quota card and the loader loaders/grok_loader.py could produce per-call token details, the adapter layer lacked adapters/grok.py, leaving the terminal report and dashboard blind to it. In addition to adding the adapter, this update synchronizes the four lookup tables that must agree: the registry's detector list, AGENT_LOADERS in the CLI and report generator, and AGENT_SHORT and AGENT_LABEL in the table UI.

FEATURE

Reports split tokens into four categories and display cache hit rates to clarify real consumption

To understand actual AI consumption, the headline "tokens burned" at the top of previous reports summed four distinct numbers into a single total, obscuring key details.

This is like a water bill that only prints a single total usage while lumping shower water, garden water, and recirculated pipe water together, making it impossible to judge whether consumption habits are healthy.

In local testing across a period of 2,565,454,499 tokens, as much as 93.8% was cache read while only 0.7% was output the model actually generated, rendering the raw total meaningless. The report now formally breaks down usage into input, cache write, cache read, and output, while calculating cache hit rates for each tool. The formula divides cache read by the sum of the three input contexts, excluding the generated output. A high hit rate indicates that old context is reused at roughly one-tenth the unit price, and the copy across all five languages explicitly frames this metric as a sign of healthy efficiency rather than wasteful repetition. The underlying layer has always recorded all four fields and previous versions merely discarded them during report aggregation, so no cache clearing or data format upgrade is required.

FEATURE

One-pass rate becomes an independent third section in the report, removing duplicates from top KPI cards

For those wanting to know which model requires the least intervention and fewest follow-up fixes, "one-pass rate" has been promoted to a standalone third section in the report.

This metric measuring whether AI completes tasks on the first attempt was already computed, but previously sat buried inside a small card under section 11 "usage habits" where most users never scrolled. It is now positioned after Insights and before Tools, with model rows using a ranked layout sorted by pass rate from highest to lowest to directly answer which model needs the fewest revisions rather than just looking at turn count. The top key performance indicator (KPI) cards also removed the duplicate one-pass rate, fixing an awkward layout where five cards were squeezed into a two-column grid without requiring any new i18n localization keys.

This is like a restaurant guide moving the "chef first-try dish success rate" from an appendix corner to a front-page column sorted from fewest dishes sent back to most, eliminating the need to crowd redundant overview numbers into the header.
FEATURE

AI roundtable incorporates Codex's default Astra model as the allowlist is no longer hardcoded

When convening an AI roundtable to deliberate issues across multiple models, you can now assign Codex's latest Astra model to the discussion.

This is like a conference room roster that rigidly invited only three senior delegates, causing security to turn away the newly appointed chief delegate at the door until the list was opened up so the new representative could take a seat.

gpt-6-astra is Codex's current new default model, but the roundtable's previous model allowlist hardcoded three older 5.6 variants, preventing the new flagship from appearing. Enabling it required no changes to pricing tables or reports: LiteLLM's price list already covers the model's four actual prices, and report color assignments match automatically on the gpt prefix, so switching works without another change.

FEATURE

"Cost burned" is renamed to "API equivalent", removing NTD conversion and clarifying gaps via subtitles

Opening the report and seeing the "Cost burned" label often gave the mistaken impression that one had actually paid that amount out of pocket.

Because this figure is merely a hypothetical number multiplied out from official list prices, it easily misled subscription users who pay a fixed monthly fee with zero marginal cost. The label is now unified across all five languages as "API equivalent", and the NTD conversion previously unique to Traditional Chinese has been removed to avoid distorting an assumed number a second time through exchange rates. The value itself remains available for pay-as-you-go API users who need it. Furthermore, because "tokens burned" counts all agents while "API equivalent" can only calculate models with published list prices, the two headline cards do not share the same denominator; a subtitle now explains the gap, but only when unpriced usage actually exists.

This is like a monthly gym member looking at a fitness tracker where burned calories are converted into an "equivalent dining-out cost" for reference, which would falsely imply wasted money if labeled as "money spent on meals today."
FEATURE

Token composition and cache hit rates switch to ranked lists, preventing tiny shares from collapsing

When a single category exceeds ninety percent, traditional stacked bar charts turn into a layout disaster.

Previously, with cache reads reaching 93.8%, the other three categories collapsed into invisible slivers, in-bar percentage text overlapped into 4.6% 0.1.93.7% at the far left edge, and legend color swatches lacked sizing styles entirely. Input, cache write, and cache read all represent incoming context while output consists of generated text, making them fundamentally distinct in nature. The presentation has now shifted to ranked lines where each of the four categories receives its own row and dedicated columns, with bars given a 2% minimum width to keep even a tiny 0.7% output clearly visible. Per-tool cache hit rates adopt the same layout sorted by hit rate, placing the worst-performing tool on the final row. Meanwhile, a test issue where mypy rejected loop variables used as keys on TypedDict types was resolved cleanly using an Any intermediate variable.

This is like a group photo where huge differences in size cause name tags to pile on top of each other, until switching to individual single-row bars makes every member's stature and standing clear.
FEATURE

Report data rows become full-width bars, aligning values across sections to a shared baseline

When reviewing data across different report sections, numbers and bars no longer jitter unpredictably between left and right.

This is like a spreadsheet where multiple sheets use mismatched column widths that scatter numbers everywhere, until establishing a unified grid and consistent label colors brings the entire report into clean alignment.

The previous layout suffered from four separate defects: two row styles (.rank-line and .tool-row) used differing column widths and gaps that placed numbers at different horizontal positions across sections; share bars were trapped inside the name column and abruptly stopped halfway across the row; every section stacked three redundant borders of section, card, and row frames; and two sections lacked column headers entirely. Data rows are now full-width progress bars, the tools section adds bar elements, and tool colors are keyed directly to the agent ID rather than sort position to avoid repainting every tool whenever rankings shift.

FEATURE

Report timeframes and comparison markers gain clarity, removing scaleless daily line charts

When tracking long-term consumption trends, the report's timeframes are now clearer and more rigorous.

The weekly burn trend section dropped its embedded daily line chart because it had no scale or values, failed to match the "weekly" heading, and provided no actionable information, while the week numbers, values, and week-over-week bars below remain unchanged. At the same time, the report clarifies its comparison baseline by unifying "vs. last month" and "vs. last week" into "vs. previous period", while the annual section is renamed "last 53 weeks" with the week count passed from program constants so the copy updates automatically if constants change.

This is like a billing receipt stripping away decorative fluctuation charts lacking scales or units, keeping only clear weekly breakdowns with changes and explicitly stating the comparison period.
FEATURE

Quota warning copy streamlined to fit inside menu bar panels without truncation

When your model quota is running low, the red warning text now displays fully within the interface.

Previously, the hardcoded nowrap warning required 320 to 470 pixels of width, but the menu bar panel text box was only 304 to 320 pixels, and because card frames hid overflowing content to preserve a retro aesthetic, the red line was cut off directly. Across 13 panels in 5 languages, Japanese suffered the most by losing 81 to 150 pixels, and English fit in only three panels. The copy is now universally shortened while preserving its original meaning, and the head-to-head World Cup panel provides an ultra-short variant that omits the reset time, fitting neatly into the narrow 151 pixels on each side.

This is like a fixed-size luggage tag where lengthy handwritten warnings get cut off at the edge, but switching to a concise message displays the full reminder cleanly.
FEATURE

Year ledger is no longer silently cleared on version mismatches, safeguarding historical records

A full year of accumulated AI usage history will no longer vanish silently to zero due to software upgrades.

This is like a library adopting new call number rules: it shouldn't discard entire shelves of older books as trash, but keep them on shelves for borrowing while reserving quarantine storage only for scrolls shredded beyond recognition.

The year ledger module previously had four execution paths that returned an empty ledger, the most severe being schema version mismatches; whenever developers tweaked fields and bumped the version, users worldwide quietly lost their entire history with no backups to recover from. Testing during development revealed that a single version bump caused the local heatmap to plunge from 119 days to 36. Version mismatches now merely log a warning and continue parsing older data day by day, moving files into the ~/.usage/quarantine/ directory as isolated backups only when they are genuinely unreadable or structurally corrupted to protect historical records.

BUGFIX

Bare repo worktrees no longer split one project into two, cleaning suffixes and repairing history

When creating a worktree from a bare repository, the same project will no longer be split into two separate entries in reports.

Previously, the project name resolver resolved worktree paths back to the main directory and took the basename directly, leaving the project name with an unwanted .git suffix. This caused path-only Claude to report obsidian00 while the other three loaders reported obsidian00.git; locally, this amounted to 5997 entries against 3732, splitting the same project in the report into 21.70% and 10.80%. All three architectural layers have been fixed: the resolver strips the trailing .git, the Codex shard cache was bumped to re-parse 28 old shards, and the year ledger folds .git back into the base project name at read time.

This is just like a branch office being logged as two separate businesses in accounting ledgers simply because its sign had a file extension printed on it, until unified consolidation merges the figures back together.
FEATURE

Token units no longer miscalculate tiers on round-up, recalibrating automatically after rounding

When your token consumption nears the boundary of a unit tier, numbers and units on reports will now advance correctly.

This is like a digital scale rounding up at 999.95 grams into a whole number but failing to switch unit labels and showing "1000.0 grams", until recalibrating the tier correctly flips the display to one kilogram.

When formatting token values, the _fmt_tokens function previously selected unit tiers from unscaled raw values, but failed to re-check whether rounding pushed the number across the tier threshold after scaling. This caused 999,950 to be printed as an awkward 1000.0K after rounding, and 999,950,000 as 1000.0M. Unit tiers are now re-evaluated after rounding to ensure units advance properly.

Original changelogGrok arrives in usage reports and the interactive dashboard with four synchronized lookup tables
**Grok now appears in the report and the interactive dashboard.** The menu bar has carried a Grok quota card for a while and `loaders/grok_loader.py` could already produce per-call token detail, but there was no `adapters/grok.py`, so both `usage report` and the dashboard were blind to it. The adapter was added along with the four lookup tables that have to agree: the registry's detector list, the `AGENT_LOADERS` maps in `usage_cli` and `reporter`, and `AGENT_SHORT` / `AGENT_LABEL` in `ui/tables`.
Original changelogReports split tokens into four categories and display cache hit rates to clarify real consumption
**The report breaks tokens into four kinds and shows each tool's cache hit rate.** The headline "tokens burned" was one number summing four different things; locally, 93.8% of a 2,565,454,499-token period was `cache_read` and only 0.7% was output the model actually generated, so the total said nothing. `UsageEntry` has always carried all four fields and `loaders/disk_cache_common.py` serialized all four — `reporter` was dropping them when it built the summary, so no cache and no schema version had to change. Cache hit rate is `cache_read / (input + cache_creation + cache_read)`; output is excluded because it is generated, not sent in. A high rate is the healthy end — old context reused at roughly a tenth of the price instead of re-sent at full rate — and the copy in all five languages is written to keep it from being read as "most of my tokens are wasted repeats."

It is now a full section placed after Insights and before Tools, and the model rows use the report's existing rank-line layout sorted by pass rate rather than by turns — the question the section answers is which model needs the least going back over, not which one is used most. No new i18n keys were required.
