Muse Code 1.4.15

Released: 2026-11-13

Release notes

FEATURE

Co-drive the same session across devices

When switching between desktop and terminal, trying to step into a running session (the execution unit for AI conversations and tasks) partway through used to lock you out.

A dual-control training car used to let only one person inside to operate it, whereas now multiple operators can ride together and queue commands, with whoever takes over first serving as the main driver.

When multiple clients connect to the same session host, session/resume now joins as a co-driver instead of returning sessionInUse, submitted requests run in order or cut in to replace as requested, and driveHolder marks the earliest driver. When connected via muse serve --listen, only the current driver can adjust the approval mode and permissions, while other connections receive drive_required and can take over with session/resume once the driver disconnects. The session discovery limit increases from 64 to 128 local and Claude records, while discoverable live sessions per machine remain capped at 64 for now. Common commands:

muse sessions --json          # List local sessions, who opened them, and whether they can be attached
muse sessions --watch --json  # Continuously print session start and end activity
muse attach <session-ref>     # Attach as a second driver; invalid references refuse with the reason and open no window
FEATURE

Host sessions independently and keep running after disconnect

When connecting to a background host locally or over SSH, you may need a session that keeps running after input ends. muse attach --stdio connects the client's standard input and output to the host holding the session, or starts one with the given flags if none exists; a newly started host does not accept --trust-workspace. If occupied by a TUI, muse exec, or an older version, it returns exit code 4. Sessions opened or forked from that connection are listed in muse sessions and can reconnect to the same host while it is still running. A host started by attach lists that session from its first session/list with spawnedBy, even if the previous host exited before finishing indexing.

muse attach --stdio <SESSION_ID> [-- <serve flags>] # Attach to or start a dedicated host, same locally and over SSH
muse serve --per-session # Start a new host per connection that lists its sessions so another client can open and operate them with muse attach --stdio <id>; does not accept --trust-workspace, keeps running after disconnect, sends no session/closed, and writes diagnostics to a log file
BUGFIX

Keep observer connections from taking drive or unloading active chats

When multiple plugins or interfaces connect to the same session at once, connections that only want to check status or exit can easily disrupt whoever is working. Calling session/resume with admitOnly: true only checks without joining as a driver, sends no session/driveChanged, and does not re-send pending approval or user-input requests; omitting admitOnly still joins as a driver. In muse serve, calling session/leave on a chat driven by someone else returns sessionInUse without unloading it. When an observer calls turn/unqueue, approval/decide, or userInput/* to settle, it returns sessionInUse and explains how to join as a driver if another client is still driving; it settles only when no one is driving, without taking drive. Viewing prompts and replaying settled commands remain available.

BUGFIX

Improve hosted session slot allocation and attach error guidance

When only 16 of the 64 local slots remain free, sessions opened via muse serve --per-session or as additional sessions over the same muse attach --stdio connection stop being listed in muse sessions to reserve room for terminals and muse exec; each Desktop tab's own session, along with its forks and side chats, still registers up to the 64-slot limit. After an upgrade, muse attach <session-name> prints "indexing session names after an upgrade..." while waiting for indexing. When attaching from a terminal to a session on a muse serve host, it now immediately reports that it cannot join yet and to keep using the window running it, instead of opening the resume picker and falsely reporting the session as already in use. Neither type of host is blocked from accepting connections or ignores SIGTERM due to a slow session anymore; if a stop timed out and the last client has left, the host exits once the stop finishes. The start log is still kept when giving up on a slow-starting host.

FEATURE

Send messages to running sessions from the command line

When coordinating multiple sessions, it used to be hard to pass a message directly from a terminal to a running conversation.

Picture an inbox hanging on an office door: busy windows used to block anyone from getting in, but now anyone from outside or the same office can slip a note straight through, and the sign-off log moves right along with the folder.

You can now send messages directly from the command line to running Muse sessions, and even from within the session itself. When the session-protocol client is on, incoming messages arrive in real time, pending queue rows show the sender, effect label, and body, and delivered messages appear directly in the transcript. The peer-message history index is now saved as a file inside the session folder, so copying the folder to another machine resumes directly without rebuilding it.

BUGFIX

Fix acceptance status and stalls in cross-session messaging

When sending messages across sessions, Linux previously often showed an uncertain status even after delivery, and messaging could stall. Running session-message send on Linux now properly reports success as soon as the target session accepts the message, and messages sent from inside a session are clearly marked as accepted instead of unverified. In pending message batches, items whose delivery is not yet confirmed keep their "sent" mark instead of having their status wiped. Sending a message is no longer stalled by another conversation updating the session list.

FEATURE

Stream narration labels in real time and emit model start events

Interfaces connected over the session protocol used to get stuck on a blank state while the model prepared to act or switched between tools.

Think of a news anchor putting up a "Live" or "Takeaway" banner the moment they start speaking, so viewers know the nature of the segment without waiting for the whole broadcast to finish.

Narration between tool calls now streams word by word just like final answers, marked as narration or answer from the very first word. The save format is unchanged so older Muse versions can still open these chats, and clients that ignore the mark see no difference. The protocol emits turn/modelAttemptStarted before contacting the model provider, allowing interfaces to show thinking only while actual work is underway. In the TypeScript SDK, ViewEvent and StaleDroppableMethod now include this event, so code that exhaustively matches all event types needs a new case. When a follow-up from the previous turn is still waiting to start, a queued prompt also reports its own turn properly so clients waiting on it receive the answer.

Side chats opened via the protocol keep the parent session's workspace and model intact. Configured MCP (a protocol that connects AI to external tools) tools are inherited as well, and resuming a session with a side chat no longer fails. A forked chat keeps its folder, model, and provider in the list after its first turn, and forks opened in the terminal now load cleanly in all clients. Origin fields have also been clarified:

BUGFIX

Preserve hosted model and recovery settings and support one-shot calls

When integrating Muse into external programs, you may want to run a single generation or keep your settings intact after a restart.

Inside a recording studio, you can run a one-off test take and call cut anytime, while keeping your tuned tone and backup plan saved for long-term bookings.

Clients connected through muse serve can run a one-shot model generation without creating a session and cancel it. When finished, it returns the text, stop reason, model name, and token (text unit for AI processing and billing) counts. The host remembers the recovery mode chosen when starting or resuming and reports both the mode and its source on read; a model chosen by an app or SDK at launch no longer reverts to the default in session lists or after restarts. Resuming over the protocol with modelId also records the specified model just like muse resume --model, and if the host refuses it, the session keeps its saved model without failing the resume.

FEATURE

Align titles, cursors, and event order in the hosted protocol

When developer tools connected via a standalone muse serve, there were gaps compared to the embedded version in naming, data structure, and startup event order. Sessions created with a plain session/start now generate an automatic name available via session/read at start and after the first turn, while titles are generated when automatic naming is enabled. Unpriced usage before the first model reply no longer sends "cost": null so strict schema-checking clients do not reject it, and muse serve --listen now matches stdio mode by sending the session/started notification before returning the session/start result. New view cursors use the v9: format, older cursors receive a one-time refusal advising "reopen without a cursor", and older view caches are automatically rebuilt on first use so events are no longer skipped or misread.

BUGFIX

When operating long conversations or switching settings through external apps, reads used to fail easily or trigger false error notices. Oversized sessions (the execution units of an AI conversation) now return pageable history so they no longer exceed the outbound frame limit, and resuming after a normal session/leave no longer falsely reports that the last run ended abnormally. When resuming or forking a chat in muse serve, if the saved reasoning effort ultra is temporarily unavailable, it falls back to xhigh while keeping your preference. Once ultra becomes available again it is reapplied, unless you reset the effort in the meantime. Resuming reads after view/unsubscribe no longer resends events that arrive concurrently, and a block from a hook (a small program triggered by a specific event) that never took effect is no longer shown as a rejection. IDE and protocol clients now warn when a paused workflow is left out of a checkpoint, and NoticeOrigin gains workflowCheckpoint.

BUGFIX

Fix SDK Queue Reclaim, Run Cancellation, and Schema Fingerprinting

When controlling a busy host with the TypeScript or Python SDK, stopping a queued run mid-way used to leave the draft unreturned or let the command run anyway. Now, aborting Session.run while its turn is queued and the host is busy keeps the SDK pulling that turn back in the background so it does not run, and cancelling again in Python returns immediately while the take-back finishes. Regardless of the order server replies arrive in, turn.unqueue now always returns the queued draft it reclaimed. After resuming a session, questions from already-finished turns are no longer listed as waiting for an answer, and importing the Python SDK from inside a source checkout reliably uses the bundled package schema fingerprint instead of picking up the live in-development schema.

BUGFIX

Track Subagent Dispatch and Multi-Level Nesting in the Session Protocol

When a main conversation dispatches work to multiple subagents—or even when subagents delegate further down—external interfaces previously had to piece relationships together from a tangled message stream.

Much like express shipping split into multi-level master and child waybills, where dispatches used to pile under one main order, each parcel now carries its upstream shipper and sign-off time so a screen refresh keeps the original order.

Clients connected via muse serve can now directly query the list of running and finished subagents in a session, getting their IDs, definition paths, parent, state, and result readiness. Protocol items also gain key markers:

ItemKind: subagentInput        # Records when each input sent to a subagent was queued and delivered, with the result naming the row it follows so clients can display rows in record order on resume
deliveredBeforeTurnEnd: true   # Marks that the subagent received the input before its parent's turn ended, distinguishing interrupted turns from finished ones on resume
parentSubagentId               # Identifies the upstream subagent that spawned this one, filing nested subagents under their parent instead of the root session
BUGFIX

Enforce Subagent Stop Controls and Report Exact Refusal Reasons

When urgently stopping a stray subagent or its own subagents, stop commands used to fail to halt execution or return only a vague refusal. Now, requesting through muse serve and the SDKs to stop a subordinate started by another subagent, or typing /stop all directly in a subagent's thread to stop its own subagents, actually terminates execution without failing; issuing a stop after sending another message to a subagent also ends its running work instead of merely marking it cancelled. Requests refused by muse serve (to interrupt, stop, resume, reopen, or close) no longer return a generic error, and instead name the exact reason, such as owner_not_running or attempt_history_unavailable. Stopping a subagent that has already stopped now returns subagent_already_stopped instead of subagent_state_ineligible, letting clients tell that race apart from a failed stop.

BUGFIX

Deliver Full Subagent Results and Cut Redundant Polling and Reports

When a parent agent handed off long research to a subagent, any result over 512 characters used to force the parent to spawn a separate reader for the rest or keep launching new watchers to poll.

When a team member finishes a long investigation report, the manager no longer needs to send someone to copy it or hold frequent check-ins, and can simply read the full document from the designated filing cabinet.

Now, when a subagent delivers its result on its own, it includes where to read the whole answer rather than only the first 512 characters, and subagent guidance instructs the parent to fetch truncated answers itself, poll long waits without spawning a fresh watcher per round, and stay silent when there is nothing new to report. Agent cards now display the total number of tool calls, a recovered child view shows its retained result after an explicit result read instead of an empty slot, and subagents receive a reminder to submit required results before hitting their step limit.

BUGFIX

Fix Subagent Disconnects After Compaction and Resume Conflicts

When the main conversation had already gone through context compaction, or when background tasks and subagents resumed together after a restart, subagents used to lose contact or wake up repeatedly. Now, sending a message to a subagent after the parent conversation is compacted no longer fails, and a resumed subagent turn waits for any background task wake or compaction install to finish before running instead of blocking compaction checkpoints alongside it. Calling session/read on a subagent's session no longer keeps a delivered input marked as queued if the parent already read the change earlier. Its corresponding worktree (a feature for opening multiple parallel copies of a project) also stops staying marked as active. Retrying a subagent when execution recovery is unavailable returns the saved creation result, and interrupted subagents no longer fail or wake repeatedly when background commands finish.

BUGFIX

Keep Subagent Progress Consistent Across Turns and Reopened Chats

When interrupting and reopening a long conversation involving subagents, the view used to drop old records, show failures as finished, or repeat completion notices. Now, resuming a compacted session cleanly restores subagents that finished before the checkpoint, and reopening a chat preserves subagent Stop information without repeating completion messages or marking new child work as finished. A subagent's view keeps its activity in order across multiple parent turns, and cancelled or failed attempts no longer read Result ready; when resuming an interrupted subagent through muse serve and the SDKs, a late result from the previous run is no longer shown while the new run is working. A resumed subagent that exhausts its reminders without submitting an answer now explicitly reports a missing answer instead of returning an empty success.

FEATURE

Workflows Read and Write Complete Reports in Original Order

When you launch a multi-agent workflow for research and synthesis, bulky reports turned in by members used to get truncated midway or misnumbered.

Magazine editors compiling a special feature used to keep only the opening paragraphs and stack articles in whatever order they arrived; now every contributor's full draft stays intact and is numbered by the original outline.

Workflows can now read complete results from finished agents (units that execute tasks within a workflow), and research workflows can also keep using large complete results through verification and report synthesis. Earlier results are no longer overwritten and lost after a subagent sends a follow-up. In the muse serve session (the execution unit of an AI conversation) protocol, a finished workflow now lists its agents in the workflow's own order rather than the order they started, so every client numbers them the same way. Guidance for workflow children reading prior reports and quoting report fields has also been clarified, requiring them to decode fields before quoting verbatim, keep literal escapes, and place commentary outside the quotes.

BUGFIX

Workflows Strengthen Fault-Tolerant Retries and Settlement Reporting

When a multi-agent workflow was wrapping up or hit a brief disk error, a single minor hiccup used to fail the whole chain. Now, if a script has already finished but hits a brief record-read failure while building its summary, it automatically retries for a short while and only fails with a message stating its records could not be read if the read keeps failing. Even when a workflow script handles a single failed agent call internally and finishes cleanly, Muse no longer mistakenly tells the main conversation's AI agent that the workflow failed, so it no longer reports a finished workflow as failed. When one agent cannot confirm that its start was saved (for example, because the disk is full), previously missing failure notifications are restored, and the remaining agents keep running as normal instead of being stopped with it. Once a session storage error clears, finished agents no longer revert to scheduled or running when settling, and scripts preserve their complete return value, including partial status and remaining work.

BUGFIX

Long-Running Workflows Lift Checkpoint Limits Without Losing Compacted Turns

During long sessions running workflows repeatedly, old checkpoints carried every child of ended workflows until saving failed at around 2,000 children.

Students do not need to haul two thousand graded exams from past terms to school every day—carrying only today's textbooks keeps the backpack zipper from bursting.

Children of ended workflows are no longer written to new checkpoints, and assigning work to such a child now explains that the workflow has ended. After resuming a long chat, new agents under the same parent can no longer reuse the name of a child from a long-finished workflow (both types of records require a newer app version to open). Reopening a compacted chat no longer drops completed workflow turns. Compaction still works after pausing a workflow, and even if compaction happens before any session checkpoint is written, it remains resumable after a restart—or, if it cannot be saved in the context, Muse explicitly states it can only be resumed in this session. When a capacity record loses its launch record, only that workflow's children cannot resume after a restart, while the chat keeps saving as usual.

FEATURE

Interrupted Workflow Recovery Preserves Results and Explains Reruns

When the app restarted unexpectedly or you paused a mid-run workflow, recovery used to stall on task-history errors or force a full rerun. Now, when you use muse workflows recover --apply to recover or resume a workflow interrupted in Muse Code 1.4.5 or earlier, finished agent calls are kept, only items that were still running are rerun from the start with each rerun's model noted, and results completed before a pause plus any stopped state are preserved across restarts. Both the task-history error and retries interrupted before their first model request have been resolved so they can continue right after a restart. If recovery halts because an agent's start record is damaged, both the result and the Latest error row now state the plain reason and next step instead of throwing only an error code.

BUGFIX

Workflow Completion No Longer Blocks Other Session Wake-Ups

When an individual agent in a workflow finished or got stuck, it used to knock out alarms and background notifications for the entire conversation. Now, after a workflow member finishes, background task results, scheduled check-ins, and watcher events still wake an idle session normally. If a single member's results are temporarily unclaimable, only that member's update waits, while the parent conversation and other sessions still wake as usual. Running workflow members also no longer have background-command reminders queued before their turn finishes, preventing them from being interrupted mid-turn and failing to submit results. When resuming a paused workflow, previously completed child results are also kept intact.

FEATURE

Added /cron Management and Improved Goal Pausing and On-Time Wake-Ups

Handing a long-term goal or scheduled check to the AI used to leave you guessing when a job was set or how to wake it after pressing Esc to pause.

Setting a clear timer for a slow simmer beats lifting the pot lid every few minutes—you can check the remaining schedule anytime and hear the bell right on cue.

The agent now leaves a notice when creating a goal or scheduled job, and entering /cron lists or removes scheduled jobs. When a goal waits on an external condition with a known end time (such as a stress test or cooldown), the agent schedules a one-time wake-up just after that time instead of only snoozing. During the repeated hour when daylight saving time ends, hourly or faster scheduled prompts still fire on both passes, while pressing Esc to pause a goal now highlights the pause notice, names /goal resume in the status bar and in a reminder after your next message, and /goal lists available commands.

BUGFIX

Fixed /goal Resume Startup and Progress Reminder Counting

Long-running /goal mode previously often looked active on the surface while doing nothing during resumes or autonomous progress. Now, entering /goal resume during a running turn or !shell command, or right as the goal reminder pauses the goal, reliably starts the resumed turn; if that turn ultimately fails to start, the terminal switches the goal back to paused so you can enter /goal resume again. An active /goal keeps working on its own after a reply that did not advance it instead of waiting idle for your next message, and background task results arriving after a resumed goal turn wait for the next turn rather than running concurrently and refusing compaction checkpoints. Progress reminders are also fixed to count once per model call, firing after about 30 calls without reported progress as designed instead of popping up early at around 15.

BUGFIX

Goal Mode No Longer Stalls with Watchers or Chat Compaction

When running long tasks in /goal mode, combining background watchers, chat compaction, or workflows used to leave the goal stuck midway. Now, while a goal reminder is active and only a long job's watcher result remains, the agent ends the current turn to let the watcher notification wake it instead of polling in a loop; background commands the agent stopped itself or saw finish while checking are no longer counted as still running, so reminders can bring the agent back to unfinished work. On the storage and compaction side, Goal recovery stays usable even if compaction leaves behind a paused workflow. When a Goal turn ends while a workflow is still running and finishes later, the session no longer skips saving its compaction checkpoint, and pausing or editing a goal during compaction preserves its resume point.

BUGFIX

Hidden Goal Prompts Stay Private and Broken Reminders No Longer Block Chats

When browsing past /goal chats or restarting a session with broken cron and reminder records, internal system text used to show up or keep the entire chat from opening. Sessions started with /goal now display your first prompt (or no title until you enter one) in the /resume list and across apps, and previews no longer mistake hidden goal prompts for your messages. If startup finds a reminder naming a nonexistent tool or a malformed tool token (syntax unit), the TUI and tbh exec disable that reminder while naming the issue and how to fix it, whereas tbh serve currently disables it silently. Chats still reopen if the reminder list is lost across a restart, and if loading quarantines a corrupt cron database, session/resume displays a warning row once.

FEATURE

Untrusted Workspaces Disable MCP and Tighten Sandbox and Write Approvals

For projects of unknown origin, vet first and allow later.

Entering a warehouse with an unverified owner means cutting power to external tools first and only jotting down notes after you sign off.

In an untrusted workspace, no MCP (Model Context Protocol, a standard for connecting AI to external tools) servers start, project configs are neither read nor listed while showing the withheld count and reason, and /mcp marks them as "withheld: workspace untrusted". After you trust the workspace, they start on the next session. Before writing to memory, the agent must show the contents and ask for approval. In muse serve, subagents and workflow agents now inherit the parent session's approval mode: allow-all sessions no longer prompt for subagents, and in deny-unmatched sessions, workflow agents deny directly without asking. When a command asks to run outside the sandbox (isolated execution environment), you can choose to always allow it in that workspace, though older versions cannot resume a session that showed this option; Windows sandbox setup at startup first explains the purpose of two local accounts and asks Yes or No, exiting without changing any settings if you choose No.

BUGFIX

Close Sandbox Network Redirect Flaws and Ask Before Domain Lookups

Commands running in a sandbox (an isolated execution environment) used to look up domains secretly before connecting, and concurrent commands risked being redirected to local services.

Visitors to a gated community must get a resident's nod before the front desk dials the intercom to check a unit number, keeping outsiders from snooping or swapping the destination.

Now any connection to a new host requires your approval before looking up its domain, including hostnames that do not exist; only localhost is checked first to confirm it points to this machine. The Linux sandbox also closes the loophole that let a command redirect its own or a concurrent command's connection to another local service. The shell argument now accepts only bash, zsh, or sh, or PowerShell or pwsh on Windows, while any other value falls back to the default shell. That ensures an approved command always runs in the shell you expect. Multiple sandboxes entering or exiting at the same time in the same workspace or session (an execution unit of an AI conversation) no longer fail at random with "Can't find source path". Any hook (a small program triggered by specific events) fired alongside them is fixed for concurrent starts and stops as well.

BUGFIX

Protect Settings and Sign-In Credentials From Overwrites, Side-Channel Reads, or Oversized Files

Folders holding account sign-in details and app preferences are vulnerable to commands peeking through side paths, overwriting them, or overloading them with huge files.

Sealing every hidden door behind a document safe and blocking oversized parcels stops anyone from sneaking in through a side corridor or forcing too much inside.

Now a ! shell command run in a session hosted by muse serve can no longer write to the folders where client credentials and settings live. On Linux, sandboxed commands and file tools can no longer read settings folders such as ~/.config/muse through a second mount point, including WSL's /mnt/wslg/distro and extra bind-mounted home directories; on those machines, a subagent started before updating may lose its work tools after /resume, and commands walking the second mount report those folders as unreadable. Settings, credential, and trust files larger than 16 MiB are also rejected with an error instead of being loaded whole into memory.

FEATURE

Strictly Verify Session Startup Paths and Permissions on Shared Computers

When starting an isolated host on a shared computer, if a parent folder or link belongs to someone else, they could secretly swap out the folder or link.

Storing a vital toolbox in a shared dorm means more than locking the box—you also check who owns the hallway doorknob and whether the envelope seal was tampered with.

Now Muse refuses to trust its local session registry folder or a session host's startup folder whenever a parent directory is owned by another local user, and it will not start a host through multi-layer folder links owned by someone else. When a folder path is too long, muse attach --stdio and muse serve --per-session start under /tmp/tbh-<uid>-rt only if it is owned by you, has mode 0700, and is not a link (creating it automatically if missing), otherwise stopping with instructions on how to fix it; any startup file altered after being written is also refused.

FEATURE

Strengthen Automatic Secret Redaction While Preserving Plain-Text Mentions

When sending error reports or letting AI read system errors, the big risk is uploading real passwords—yet being overly sensitive can blot out normal text beyond recognition.

Newsroom editors black out a real card number in a photo without cutting the words "credit card" out of the article, preventing leaks while keeping communication intact.

Now a Meta API key after Bearer or Authorization: token (an authorization credential) is hidden whole from the model's view, session logs, and error output, while plain mentions like "JWT bearer tokens" in answers or tool results reach the model unchanged instead of inserting a redaction marker it might copy into code. Before /feedback uploads anything, connection-string passwords, authorization headers, JWTs, common keys, and text following token: or password: in your note, recent activity, crash reports, screen snapshot, and configuration snapshot are automatically masked as [REDACTED].

BUGFIX

Wait Quietly for Automatic Reports on Long Background Tasks Instead of Polling

Previously, when you had AI run a slow command like a build or test in the background, it would often keep checking progress impatiently, sometimes stalling for up to five minutes and missing the finish notice while wasting several conversation turns.

Tossing laundry into the washing machine lets you get on with other chores instead of standing at the door checking if the spin is done, coming back only when the chime rings.

Now whenever the only work left is a background job the agent started, it ends the current turn and lets the completion or stuck-job notice wake it automatically; background status results also remind it that the result arrives automatically, so it stops spawning new shell commands to check logs or processes and uses the Monitor tool if it actually needs to watch progress. Even when a background task wakes the agent just to report that it is still running, the agent ends that check quietly instead of spending an extra model call on a summary.

BUGFIX

Resume Parked Conversations Immediately When Tasks Finish

Previously, when waiting on a watcher or background command for results, a conversation could stay stuck on "Working" or leave arrived results stranded for hours until you pressed a key or sent a message. Now a parked session resumes immediately and hands control back to the agent whenever a watcher started through either the standard path or the canonical Monitor path emits change lines, a watch task ends, or a background job finishes. Background-task results and monitor events queued while the chat sits idle are also delivered directly instead of waiting for your next keypress.

BUGFIX

Prevent Background Wakes and Active Turns From Colliding or Stopping Early

FEATURE

Remove Duplicate Session-Log Copies to Cut Resume and Growth Memory

Previously, resuming a long session or continuing a conversation kept an extra duplicate copy in memory, even storing every old and new log record twice just to verify its original bytes. Now background-task and subagent records read back from the session log are no longer stored twice, and each line of a long session without a checkpoint is no longer held twice while loading, sharply reducing peak memory during resume. For both resuming and subsequent writes, log records no longer keep a second copy to prove their original bytes, and the task and run state kept for later appends no longer duplicates records the session already holds, so memory grows more slowly over long chats.

FEATURE

When launching a batch of new sessions at once or reopening a long chat, the internals used to reserve oversized spare buffers, duplicate queued messages and event indexes, and flush to disk frequently during creation. Now, when bursts of new session requests arrive through muse serve, writing to the scheduled-task store performs fewer disk flushes so creation finishes sooner. When resuming a long chat, the live session log no longer holds an extra spare buffer sized for every record, and the replay check kept for later checkpoints no longer stores a copy of every queued message; the index that matches recorded copies of run and approval events also keeps each copy only once, keeping memory light during long runs.

FEATURE

Unload Finished Subagent Chats After Reading and Trim Workflow Views

After a long session ran multiple workflows and dozens of subagents, their entire conversations used to stay stuck in memory even after they finished or failed.

Now reading a finished subagent's task state no longer keeps its whole conversation in memory; finished subagent conversations are unloaded after they are last read, and subagents in a workflow that fail or end without a result are unloaded once the workflow reads their outcome. When resuming a long chat, the subagent view no longer keeps its own copy of all past events, and the workflow view now records only each agent's tool calls and token (the text unit AI processes and bills by) usage instead of holding onto the entire run.

FEATURE

When build or test commands poured output across the screen, or after spawning many subagents and workflows, the same command output used to be stored three times in memory, and recent output from finished background tasks was stored twice. Now Muse Code cuts large command output from three copies down to one, and both recent output from finished background tasks and kept run events in resumed long chats are stored only once (instead of living in both the run history and the model context view). FEATURE

If muse serve stayed running as a persistent service for days, serving dozens or hundreds of sessions (units of AI conversation), memory used to keep climbing with the number of sessions served even when clients left early.

Now, as soon as a session is left or unloaded, muse serve fully frees its memory; each loaded but idle session consumes less CPU, and starting a new session stays lightweight even with many sessions loaded at once. For a long session that is simply resumed, both peak memory during recovery and resident memory while it stays open in the background are lowered as well.
