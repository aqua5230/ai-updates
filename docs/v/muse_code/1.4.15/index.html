Muse Code 1.4.15

發布日期：2026-11-13

繁體中文

新功能

多端接手同一個工作階段並肩操作

你在桌機與終端機之間切換時，想半途插手正在跑的工作階段（AI 對話與任務的執行單位），以前總會被擋在門外。

就像裝了雙方向盤的教練車，過去只許一人上車操作，現在多位操作員能同車排隊送出指令，誰先接手就由誰當主駕駛。

多個用戶端連上同一台工作階段託管主機時，session/resume 會改以共同駕駛身分加入，不再回傳 sessionInUse，送出的請求依序執行或依要求插隊替換，並由 driveHolder 標出最早的駕駛。透過 muse serve --listen 連線時，僅現任駕駛能調整核准模式與權限，其餘連線會收到 drive_required，等駕駛斷線即可用 session/resume 接管。工作階段探索上限從 64 筆拉高到 128 筆本機與 Claude 紀錄，單機可探索的即時工作階段仍暫限 64 筆。常用指令：

muse sessions --json          # 列出本機工作階段、開啟者與可否接上
muse sessions --watch --json  # 持續印出工作階段啟動與結束動態
muse attach <session-ref>     # 以第二駕駛接上；無效參考會寫明原因拒絕且不開窗
新功能

獨立託管工作階段並在連線斷開後持續運作

從本機或 SSH 連接背景主機時，你可能需要輸入結束後仍運作的工作階段（AI 對話的執行單位）。muse attach --stdio 會把用戶端的標準輸入與輸出接上持有它的主機，沒有就以指定參數啟動；新啟動的主機不接受 --trust-workspace。若被終端機介面、muse exec 或舊版佔用，回傳結束碼 4。從該連線另開或分支的工作階段會列入 muse sessions，主機仍運作時可連回同一主機。attach 啟動的主機從首次 session/list 就會列出該工作階段並附上 spawnedBy，即使前主機未完成索引就退出也一樣。

muse attach --stdio <SESSION_ID> [-- <serve flags>] # 接上或啟動專屬主機，本機與 SSH 皆同
muse serve --per-session # 每條連線開新主機，該主機會列出自己的工作階段，讓另一個用戶端能用 muse attach --stdio <id> 開啟並操作；不接受 --trust-workspace，斷線後持續運作，不送 session/closed，診斷寫入日誌檔
問題修復

旁觀連線不搶駕駛權也不強行卸載別人對話

多套外掛或介面同時連著同一個工作階段（AI 對話的執行單位）時，只是想查看狀態或退出的連線很容易誤傷正在工作的人。session/resume 帶 admitOnly: true 只檢查不加入駕駛，不送 session/driveChanged，也不重送待核准與待輸入請求；未帶 admitOnly 仍會加入駕駛。muse serve 中 session/leave 離開他人駕駛的對話會回 sessionInUse，不卸載。旁觀者呼叫 turn/unqueue、approval/decide 或 userInput/* 結算時，有其他用戶端仍在駕駛就回 sessionInUse，並說明如何加入駕駛；無人駕駛時才結算，且不取得駕駛權。查看提示與重播已結算指令仍可用。

問題修復

改善連線託管槽位分配與附接錯誤引導

64 個本機槽位只剩 16 個空位時，經 muse serve --per-session 開啟或在同一 muse attach --stdio 連線另開的工作階段，會停止列入 muse sessions，替終端機與 muse exec 留位；桌面分頁本身及其分支、側邊對話仍註冊到 64 筆上限。 升級後 muse attach <session-name> 會印「indexing session names after an upgrade...」等待索引。從終端機接上 muse serve 主機的工作階段時，會立刻告知暫時無法加入、請繼續用原本執行它的視窗，不再跳出恢復清單並誤報已被使用。 這兩種託管主機不再被慢工作階段卡住連線或忽略 SIGTERM；若停止曾逾時且最後一名用戶端已離開，停止完成後就退出。放棄慢啟動主機時仍保留啟動日誌。

新功能

從指令列傳訊給執行中的工作階段

讓多個工作階段（AI 對話的執行單位）彼此協作時，過去很難從終端機直接對正在跑的對話傳話。

宛如掛在辦公室門口的收件夾，以前忙碌中的窗口進不去，現在從外部或同一間辦公室都能直接遞紙條，簽收目錄還會跟著資料夾一起搬走。

現在你能直接從指令列傳訊給執行中的 Muse 工作階段，甚至從工作階段本身發送也可以。當工作階段協定用戶端開啟時，外部送來的訊息會即時抵達，待處理佇列列會顯示寄件者、效果標籤與內文，已送達的訊息則直接進駐對話紀錄。互傳訊息的歷史索引也改存成工作階段資料夾內的檔案，整包複製到另一台電腦就能直接恢復而免去重建。

問題修復

修好跨工作階段傳訊的受理狀態與卡頓

跨工作階段（AI 對話的執行單位）互相傳訊時，之前在 Linux 上明明送出卻常顯示不確定，傳訊也可能卡住。現在於 Linux 執行 session-message send，只要目標工作階段收下訊息就會正確回報成功；從工作階段內部發出的訊息，也會明確標為已受理，不再顯示為未驗證。 在待處理訊息批次裡，送達尚未獲確認的項目仍會保留「已送出」標記，不會回頭被抹掉狀態。現在傳訊不會再被另一個正在更新工作階段清單的對話拖住。

新功能

串流旁白即時標記與模型啟動事件

連接工作階段（AI 對話的執行單位）協定的介面，過去常在模型準備動手或工具切換時卡在空白。

新聞主播開口就掛上「現場連線」或「結論」字卡，觀眾不用等整段播完才知道內容的性質。

現在工具呼叫之間的旁白會像最終回答一樣逐字串流，從第一個字就標明旁白或回答。存檔格式沒變，舊版 Muse 仍能開啟這些對話；忽略標記的用戶端也看不出差別。協定會在聯繫模型供應商前送出 turn/modelAttemptStarted，讓介面只於真正運算時顯示思考中。TypeScript SDK 的 ViewEvent 與 StaleDroppableMethod 加入該事件，逐一比對所有事件種類的程式須新增處理分支。上一回合的後續動作還在等啟動時，排隊提問也會正確回報自己的回合，讓等待該回合的用戶端收到答案。

問題修復

分支與側邊對話繼承設定並對齊來源標記

從主線分岔出實驗性對話或側邊討論時，過去切換不同視窗打開常會遺失設定甚至開不起來。

猶如從盆栽母株剪下一段分株，以前移盆常弄丟配方與名牌，現在不但帶著原本的土壤與養分，來源標籤也寫得清清楚楚。

由協定開啟的側邊對話，會完整保留母工作階段（AI 對話的執行單位）的工作區與模型。原本配置的 MCP（讓 AI 連接外部工具的協定）工具也會一併繼承，恢復帶有側邊對話的工作階段不再失敗。分支對話在首回合後會於清單保留資料夾、模型與供應商資訊，在終端機開過的分支也能在所有用戶端順利開啟。來源欄位也已釐清：

forkedFrom.isRewind  # 協定讀取分支時標明是否來自對話倒帶
sideFrom             # 側邊對話的 session/resume 改填此欄，剛開時 session/list 為 null
問題修復

保留託管模型與復原設定並支援單次呼叫

把 Muse 接入外部程式時，你可能只想跑一次生成，也可能希望重開後設定別跑掉。

錄音室既能單次試錄、隨時喊卡，長租時調好的音色與備援方案也會留著。

透過 muse serve 連線的用戶端，不必建立工作階段（AI 對話的執行單位）就能執行單次模型生成並取消。結束後會回傳文字、停止原因、模型名稱與 token（AI 處理與計費的文字單位）數量。主機會記住啟動或恢復時選定的復原模式，讀取時回報模式與來源；應用或 SDK 指定啟動的模型在清單與重啟後不再跳回預設值。透過協定以 modelId 恢復時，也會保存指定模型，如同 muse resume --model；若遭主機拒絕，則保留原存模型而不中斷恢復。

新功能

對齊託管協定的標題、游標與事件順序

開發工具透過獨立啟動的 muse serve 對接時，先前在命名、資料結構與啟動事件順序上和內嵌版有落差。用一般 session/start 建立的工作階段（AI 對話的執行單位）現在會自動產生名稱，啟動及首回合後可由 session/read 取得；標題則在開啟自動命名時產生。 首次模型回覆前未計價的費用不再送出 "cost": null，避免嚴格檢查結構的用戶端拒收；muse serve --listen 也會比照標準輸入輸出模式，先送出 session/started 通知再回傳 session/start 結果。新版檢視游標改為 v9: 格式，舊游標會先收到一次「reopen without a cursor」的拒絕提示，舊版檢視快取（暫存紀錄）也會在首次使用時自動重建，不再漏讀或誤讀事件。

問題修復

修復工作階段協定讀取上限與異常提示

透過外接應用操作長對話或切換設定時，以前容易讀取失敗或收到假異常通知。超大型工作階段（AI 對話的執行單位）現改用可分頁歷史回傳，不再超出輸出影格上限；正常 session/leave 後恢復，也不再誤報上次異常結束。 在 muse serve 恢復或分支對話時，原存推理力度 ultra 若暫不可用，會先用 xhigh 並保留偏好；等 ultra 可用才套回，但期間若重設力度，就不再自動套回舊偏好。自 view/unsubscribe 後接續讀取不再重送同步抵達的事件，未生效的 hook（特定事件觸發的小程式）阻擋不再顯示為拒絕。IDE 與協定用戶端會在暫停工作流程未存進檢查點時警告，NoticeOrigin 加入 workflowCheckpoint。

新功能

TS 與 Python SDK 新增高階單次執行與管理介面

寫程式串接 TypeScript 與 Python SDK 管理工作階段（AI 對話的執行單位）時，過去常得自己拼湊繁瑣的底層協定指令。

好比把裸露的電路板裝進標好按鈕的遙控器，現在按一個鍵就能跑完一輪對話並取回答案與用量。

新版 SDK 與教學文件改推高階介面，能列出任務、技能與 hook（特定事件觸發的小程式），暫停或恢復工作流程、取得回顧、送回饋、開側邊對話及搜尋已存工作階段。未傳入主機路徑時 spawn 會自動搜尋 PATH 並於找不到時列出搜尋路徑，偶有未封裝的指令也可改用 client.command 發送，但會擋下由 SDK 自行管理的指令。原文明確點名的高階介面包括：

session.run                     # 單次呼叫跑完一回合，支援取消並回傳答案、項目與 token（AI 處理與計費的文字單位）用量
MuseClient.spawn / startSession # 快速入門與食譜範例改教這些高階操作
問題修復

修好 SDK 撤回佇列、中止執行與指紋比對

用 TypeScript 或 Python SDK 控制忙碌中的主機時，先前若在排隊中途喊停，常出現草稿取不回或指令依然偷跑的狀況。現在於排隊且主機忙碌時中止 Session.run，SDK 會在背景持續把該回合撤回而不會照跑，Python 版若再次取消更能立刻返回並讓撤回繼續完成。 不論伺服器回覆順序為何，turn.unqueue 現在一定會交還成功收回的佇列草稿。恢復工作階段（AI 對話的執行單位）後，已結束回合的提問不再被列為待回答，在原始碼目錄內匯入 Python SDK 也會穩定使用套件封裝內的結構指紋，不再誤抓開發中的即時結構。

新功能

用終端機指令直接管理與登入 MCP 伺服器

平時想讓 AI 接上各種外部工具，不用再手動翻找與編輯設定檔裡的欄位了。

恰似替手機通訊錄補齊增刪查按鈕，以前得手動翻進設定檔修改格式，現在直接在終端機下指令就能把外部工具記進名冊或撤除。

現在這組管理 MCP（讓 AI 連接外部工具的協定）伺服器的指令已完整就緒，同時支援寫入個人使用者設定或專案設定檔，也修好了全新設定檔剛加入第一台伺服器後 muse mcp login 失敗的問題。常用管理指令如下：

muse mcp list      # 列出已設定的伺服器、來源、傳輸方式與登入狀態
muse mcp get       # 檢視單一伺服器的來源、傳輸方式與登入細節
muse mcp add       # 新增 MCP 伺服器到個人或專案設定
muse mcp add-json  # 直接以 JSON 格式寫入伺服器設定
muse mcp remove    # 從個人或專案設定移除伺服器
muse mcp login     # 替新增的伺服器進行登入驗證
新功能

MCP 連線代理設定、呼叫提示與報錯點名

在需要透過代理伺服器連網的公司環境，或排查 MCP（讓 AI 連接外部工具的協定）設定錯誤時，以前常只看到空白或模糊失敗。現在執行中的呼叫會直接顯示正在跑的 MCP 工具與伺服器名稱，而 MCP 伺服器與 hook（特定事件觸發的小程式）也會像其他程式一樣吃到網路代理設定。 查詢指令的診斷也更精準：當儲存庫標記無法讀取時，會直接報錯而不再悄悄略過專案伺服器；格式錯誤會點名出問題的專案檔案並正確區分非檔案路徑；純文字模式的失敗輸出也會像 --json 一樣先印出待處理警告再列錯誤。代理變數包含：

HTTP_PROXY   # HTTP 代理設定
HTTPS_PROXY  # HTTPS 代理設定
ALL_PROXY    # 通用代理設定
NO_PROXY     # 略過代理的例外清單
問題修復

協定層追蹤子代理派工與多層巢狀關聯

當主對話同時派工給多位子代理、甚至子代理底下又繼續往下派工時，外接介面先前只能從雜亂的訊息流裡硬湊關係。

好比拆分成多層子母單的快遞物流，過去所有派件全塞在總訂單底下，現在每張包裹都印著上游託運人與簽收時間，重整畫面也照原順序排好。

透過 muse serve 連線的用戶端，現在能直接查詢工作階段（AI 對話的執行單位）裡執行中與已結束的子代理清單，取得 ID、定義檔路徑、父層、狀態與結果是否就緒。協定項目也補齊關鍵標記：

ItemKind: subagentInput        # 記錄送給子代理每筆輸入的排隊與送達時間，結果附帶接續列位，讓用戶端恢復工作階段時能照紀錄順序顯示這些列
deliveredBeforeTurnEnd: true   # 標示子代理於父回合結束前已收下該筆輸入，恢復時可區分中斷或完成
parentSubagentId               # 標記發起該子代理的上層子代理，讓巢狀子代理歸位不掛回根對話
問題修復

子代理停止控制生效並回報確切拒絕原因

要緊急叫停跑偏的子代理或它底下的孫代理時，以前常喊了停卻沒停下來，或只得到一句含糊的拒絕。現在透過 muse serve 與 SDK 要求停止由另一名子代理啟動的下屬，或是直接在子代理對話串裡輸入 /stop all 停掉它自己開出的子代理，都能真正切斷執行而不報失敗；對已送出其他訊息的子代理下停止指令，也會實際終止運作而非只貼取消標籤。 在 muse serve 遭到拒絕的操作（中斷、停止、恢復、重開或關閉）也不再只回籠統錯誤，而是會點名確切原因，例如 owner_not_running 或 attempt_history_unavailable。 停止已經停下的子代理則會回傳 subagent_already_stopped，不再誤給 subagent_state_ineligible，讓用戶端能分辨這是剛好已經停了，而不是停止失敗。

問題修復

子代理完整交卷並減少無謂回報與重覆派工

主代理把長研究交給子代理執行時，先前只要結果超過 512 個字元，主代理還得另外派一位讀取員去翻後半段，或一直開新監看員輪詢。

如同接手調查的組員寫完長報告，主管不用再派人去抄寫或頻頻開會，直接去指定檔案櫃就能讀完整份內容。

現在子代理主動交卷時會附上完整答案的位置而非只給前 512 字元，指導準則也要求主代理自行讀取截斷內容、輪詢長等待時不再每輪生新監看員，沒有新進度就保持安靜。 代理卡片現在會顯示工具呼叫總數，復原後的子檢視在明確讀取後也會展示保留結果而非空白，子代理在逼近步數上限前亦會收到繳交結果的提醒。

問題修復

修復子代理於壓縮後失聯與恢復衝突

當主對話已經做過上下文壓縮，或背景任務與子代理同時在重啟後恢復執行時，子代理先前很容易失聯或反覆被喚醒。現在父對話壓縮過後再傳訊給子代理不會再失敗；恢復運作的子代理回合也會先等背景喚醒與壓縮安裝跑完才上場，不再搶在旁邊阻擋檢查點存檔。 對子代理的工作階段（AI 對話的執行單位）呼叫 session/read 時，若父層早先已讀過異動，就不會再把已送達輸入標在佇列裡。對應的 worktree（讓專案平行開多份副本的功能）也不會繼續誤顯為 active。當無法復原執行時重試子代理會回傳已存的建立結果，中斷過的這類子代理也不會再因背景指令結束而報錯或反覆醒來。

問題修復

子代理跨回合與重開後的進度紀錄一致

中斷再重開有子代理參與的長對話時，以前檢視畫面常會漏掉舊紀錄、把失敗看成完成，或重複跳出完工通知。現在恢復壓縮過的工作階段（AI 對話的執行單位）時會把檢查點前已完成的子代理整齊還原，重開對話也會保留子代理的停止資訊，不會再重複送出完成訊息或把新的子工作誤標成已完成。 子代理檢視跨越多個父回合時活動順序不再錯亂，取消或失敗的嘗試也不會再寫著 Result ready；透過 muse serve 與 SDK 恢復被中斷的子代理時，新回合運作期間不會誤貼上一輪遲來的結果。耗盡提醒卻沒交答案的恢復子代理，也會明確回報缺少答案，不再交回看似成功的空白結果。

新功能

工作流程讀寫完整報告並依原順序編號

啟動多代理協作的工作流程進行研究與彙整時，各個成員交回的龐大報告以前常在半路被截短或編號亂掉。

好比雜誌編輯台彙整專題稿件，過去只取前幾段又按交稿先後亂排，現在全員完整文稿都留存齊全，並按企劃原本大綱依序編號。

現在工作流程能從已完成工作的代理（流程中負責執行任務的單元）讀取完整結果，研究型工作流程在驗證與報告統整階段也能持續使用大型完整結果；子代理後續補件後，先前產出的結果不會被覆蓋遺失。 在 muse serve 工作階段（AI 對話的執行單位）協定裡，已結束的工作流程會依照自身定義的順序而非啟動順序排列代理，讓各介面編號一致；工作流程對子代理讀取先前報告與引述報告欄位的指引也已釐清，要求逐字引用前先解碼、保留字面跳脫字元並將評論寫在引號外。

問題修復

工作流程強化容錯重試與結算狀態回報

多代理工作流程在即將收尾或遇到短暫硬碟錯誤時，以前常因為一次小擦傷就整串判死。現在腳本本身已經跑完卻在彙整摘要時短暫讀取紀錄失敗，會先自動重試一會兒，持續失敗才會寫明無法讀取紀錄；工作流程腳本即使內部處理掉單一失敗的代理呼叫而順利收尾，Muse 也不再誤告訴主對話的 AI 代理工作流程失敗，所以它不會再把已完成的工作流程說成失敗。 當其中一位代理無法確認啟動已存檔（例如磁碟空間已滿）時，先前遺漏的失敗通知已補回，其餘代理也會照常跑完而不被連坐停掉。工作階段（AI 對話的執行單位）的儲存錯誤排除後，已結束代理結算時不再跳回排程或執行中，腳本也能完整保留含部分狀態與剩餘工作的回傳值。

問題修復

長時運行工作流程突破檢查點上限且壓縮不遺失

長時間反覆執行工作流程時，舊檢查點背著所有已結束流程的子代，累計約 2,000 個就無法存檔。

學生上學不必天天背已結業的兩千張舊考卷，只帶當下需要的課本，書包拉鍊才不會撐壞。

現在已結束工作流程的子代不再寫進新檢查點，再對該子代派工會說明流程已結束；恢復長對話後，同一父層下的新代理也不得重用早已結束工作流程的子代名稱（兩種紀錄皆須新版程式才能開啟）。 重開壓縮過的對話不再丟失已完成的工作流程回合；暫停工作流程後壓縮仍能運作，即便尚未寫過工作階段（AI 對話的執行單位）檢查點便壓縮，重啟後仍可恢復，若無法存進上下文則會明講僅限本次恢復；容量紀錄遺失啟動紀錄時，僅該工作流程的子代無法在重啟後恢復，對話照常存檔。

新功能

工作流程中斷復原保留成果並說明重跑細節

程式意外重啟或把執行一半的工作流程暫停下來，以前常卡在任務歷史錯誤或得整批重跑。現在用 muse workflows recover --apply 復原或接續在 Muse Code 1.4.5 及更早版本中斷的工作流程時，會留住已跑完的代理呼叫，只從頭重跑當時仍在跑的項目，並標出各自使用的模型；暫停前已完成的結果與停止狀態在重啟後也會妥善保留。 任務歷史錯誤與在首次送出模型請求前就中斷的重試問題都已排除，重啟後可直接續跑；若因某位代理的啟動紀錄損壞導致復原喊停，結果與 Latest error 列都會直接列出白話原因與下一步處理方式，不再只丟出錯誤代碼。

問題修復

工作流程收尾不卡住其他工作階段喚醒

工作流程底下有個別代理結束或卡住時，以前常連帶讓整個對話的鬧鐘與背景通知全部失靈。現在工作流程成員完工後，背景任務結果、定時報到與監看事件仍會正常喚醒閒置工作階段（AI 對話的執行單位）。若單一成員的結果暫時無法領取，才只有該成員的更新先等待，父對話與其他工作階段仍會照常被喚醒。 執行中的工作流程成員也不再於回合還沒跑完時被塞入背景指令提醒，避免它們半路被打岔而沒能送出結果；恢復暫停中的工作流程時，先前已完成的子代成果同樣會完整留下。

新功能

新增 /cron 排程管理並改善目標暫停與準點喚醒

把長期目標或定時檢查交給 AI 接手時，過去最怕不知它何時設了排程、或按 Esc 暫停後忘記怎麼叫醒。

好似替長時間燉煮設好明確鬧鐘，過去只能不斷探頭掀鍋蓋，現在隨時看得到剩餘安排與清單，時間一到還會準點響鈴。

現在代理建立目標或排程任務時會主動留下通知，輸入 /cron 即可列出與刪除排程；當目標等待工作階段外某個已知結束時間的條件（如壓力測試或冷卻時間）時，代理會直接排定該時刻剛過後的單次喚醒，不再只按延後提醒。在日光節約時間結束出現重複一小時的時段，每小時或更頻繁的排程提示也會兩輪照常觸發，按 Esc 暫停目標時更會強化提示、於狀態列與下則訊息後的提醒寫出 /goal resume，輸入 /goal 則列出可用指令。

問題修復

修好 /goal 恢復啟動與進度提醒計數

長程執行的 /goal 目標模式之前常在恢復與自主推進時「表面寫著運作中、實際上卻一動也不動」。現在不論是在回合或 !shell 指令執行中，還是目標提醒剛暫停目標的瞬間輸入 /goal resume，都會確實觸發恢復回合；若該回合最終無法啟動，終端機也會將目標切回暫停狀態，好讓你再次輸入 /goal resume。 啟動中的 /goal 遇到沒有接續推進的回覆後會繼續自主執行，不再乾等你的下一則訊息；恢復目標回合後才來的背景任務結果也會乖乖排進下一回合，不再併行搶跑而拒絕壓縮檢查點。進度提醒也修正為每呼叫模型一次計一次，按原設計在約 30 次沒有回報進度後才提醒，不再於約 15 次就提前跳出。

問題修復

目標模式搭配監看與對話壓縮不再卡死

開啟 /goal 目標模式執行長任務時，只要同時碰到背景監看、壓縮對話或工作流程，以前常把目標卡在半路動彈不得。現在目標提醒啟動中若只剩長任務的監看結果待等，代理會結束當前回合交給監看通知喚醒，不再空轉輪詢；由代理自己停掉或檢查時已確認結束的背景指令，也不再被誤算成還在跑，好讓提醒能叫回代理繼續處理未完工作。 在與儲存和壓縮的配合上，即便壓縮遺留了暫停中的工作流程，目標復原功能依然可用；目標回合結束時若工作流程仍在跑並在稍後完工，工作階段（AI 對話的執行單位）也不再漏存壓縮檢查點，而壓縮進行中暫停或編輯目標也能完整保留恢復點。

問題修復

隱藏目標提示不外洩並防範損壞提醒阻礙對話

翻找過去用 /goal 跑過的對話，或工作階段（AI 對話的執行單位）帶著壞掉的排程與提醒紀錄重啟時，以前常看到一堆系統內部字樣，甚至整段對話打不開。現在用 /goal 開啟的工作階段在 /resume 清單與各應用中，會改顯示你的第一句提問（未輸入前不設標題），預覽畫面也不再把隱藏的目標提示誤當成你發的訊息。 啟動時若發現某則提醒指定的工具不存在或工具 token（語法記號）格式錯誤，TUI 與 tbh exec 會停用該提醒並點名問題與修法，而 tbh serve 下目前僅靜默停用。提醒清單跨重啟遺失仍可重開對話，載入時若隔離了損壞的排程資料庫，也會透過 session/resume 顯示一次警告列。

新功能

未信任工作區停用 MCP 並收緊沙盒與寫入核准

來路不明的專案，先把關再放行。

如同進入沒確認屋主的倉庫，先斷外接工具電源，你簽了字才准寫備忘。

未信任的工作區，所有 MCP（讓 AI 連接外部工具的協定）伺服器都不會啟動，專案設定不讀不列並顯示受擋數量與原因，/mcp 標記為「withheld: workspace untrusted」。信任該工作區後，下個工作階段才啟動它們。寫入記憶前須先出示內容徵詢核准。 在 muse serve 裡，子代理與工作流程改沿用母工作階段（AI 對話的執行單位）的核准模式：全部允許的工作階段不再為子代理跳詢問，未匹配規則就拒絕的工作階段，工作流程代理直接拒絕不詢問。 指令請求跨出沙盒（隔離執行環境）時，可選擇在該工作區永遠允許該指令，但舊版無法恢復顯示過此選項的對話；Windows 沙盒啟動時先說明兩個本機帳號用途並問 Yes 或 No，選 No 不動任何設定直接退出。

問題修復

堵住沙盒網路導向漏洞並先問再查網域

在沙盒（隔離執行環境）裡執行指令，過去連線前就先偷查網域，並行指令也有被改道本機服務的風險。

比方社區訪客須先取得住戶點頭，大廳才幫忙撥內線查門牌，不讓外人趁亂探聽或掉包連線目標。

現在連向新主機必先核准才查網域，不存在的主機名稱亦同，僅 localhost 會先驗證是否指向本機。Linux 沙盒也堵住將自己或並行指令的連線重導至其他本機服務的漏洞。shell 參數現限用 bash、zsh 或 sh，Windows 限 PowerShell 或 pwsh，其餘改用預設 shell。這樣核准過的指令一定跑在你預期的 shell 裡。同工作區或工作階段（AI 對話的執行單位）裡多個沙盒同時進出時，不再隨機報錯 "Can't find source path"。連帶觸發的 hook（特定事件觸發的小程式）在並行啟停時也一併修好。

問題修復

防範設定與登入憑證遭改寫、旁路窺探或塞爆

存放帳號登入細節與軟體偏好的資料夾，最怕被指令繞道偷看、誤改或遭超大檔案撐爆。

彷彿替存放證件的保險櫃封死所有牆後暗門與過大郵包，從側邊走廊繞道或硬塞都會被門鎖擋下。

現在在 muse serve 託管的工作階段（AI 對話的執行單位）中執行 ! shell 指令，再也無法寫入存放用戶端憑證與設定的資料夾。 在 Linux 上，沙盒（隔離執行環境）指令與檔案工具無法再透過第二掛載點讀取 ~/.config/muse 等設定資料夾，包括 WSL 的 /mnt/wslg/distro 與額外繫結的家目錄；在這類機器上，更新前啟動的子代理在 /resume 後可能會失去工作工具，掃描第二掛載點的指令則會回報這些資料夾無法讀取。超過 16 MiB 的設定、憑證與信任檔也會直接報錯拒讀，不再整份載入記憶體。

新功能

嚴格驗證共用電腦上的工作階段啟動路徑與權限

在多人共用的電腦上啟動獨立託管時，如果上層資料夾或連結歸別人管，對方就有機會暗中調包資料夾或連結。

想像在共用宿舍寄放重要工具箱，不只要鎖好箱子，連走廊門把歸誰、信封封條有沒有被動過都要先逐一查驗。

現在只要本機工作階段（AI 對話的執行單位）註冊資料夾或專屬主機啟動資料夾的上層目錄屬於其他本機使用者，Muse 就拒絕信任；經由他人擁有的多層資料夾連結也不會啟動主機。 資料夾路徑過長時，muse attach --stdio 與 muse serve --per-session 只會在 /tmp/tbh-<uid>-rt 確實屬於你、權限為 0700 且非連結時（缺少時自動建立）才於該處啟動，否則停下並說明修法；寫入後遭變動的啟動檔同樣一律拒用。

新功能

加強金鑰自動遮罩並保留一般名詞討論

送出錯誤回報或讓 AI 讀系統錯誤時，最怕把真密碼連帶上傳，卻又怕過度敏感把正常文字塗得面目全非。

宛如報社編輯把照片裡的真實卡號整串塗黑，卻不會連文章裡寫著「信用卡」三個字也一併剪掉，既防外洩又不誤傷溝通。

現在出現在 Bearer 或 Authorization: token（授權令牌）後方的 Meta API 金鑰，會從模型視野、工作階段日誌與錯誤輸出中整組隱藏；但在回答或工具結果裡純粹提到 "JWT bearer tokens" 等字詞時，會原樣保留給模型，不再誤貼遮罩標記讓模型抄進程式碼。使用 /feedback 上傳前，備註、近期活動、當機報告、畫面與設定快照裡的連線字串密碼、驗證標頭、JWT、常見金鑰，以及 token: 或 password: 後方的文字都會自動遮成 [REDACTED]。

問題修復

背景長任務改為靜候自動回報，停止空轉輪詢

以前讓 AI 在背景跑編譯或測試這類耗時指令時，它常會急著一再檢查進度，有時甚至卡著等上五分鐘卻錯過完工通知，白白燒掉好幾輪對話回合。

如同把衣服丟進洗衣機就先忙別的事，不再站在門前反覆檢查轉完沒，等結束鈴響了再回來收衣服。

現在只要場上只剩代理自己啟動的背景工作，它就會直接結束當前回合，把剩下的交給完成或卡住通知自動喚醒；背景狀態回報也會主動提醒「結果會自動送達」，讓代理不再用新 shell 指令去翻日誌或查行程，真要盯進度就改用 Monitor 工具。就算背景任務中途只報一聲「還在跑」，代理也會安靜結束這次檢查，不再多耗一次模型呼叫去寫摘要。

問題修復

暫停等待的對話在任務完工時立刻恢復

先前交給監看器或背景指令等結果時，對話常停在「Working」一動也不動，或者結果其實早就到了卻卡住好幾個小時，非得你主動按一下鍵盤或傳句話才肯往下跑。現在不論是用一般路徑或正規 Monitor 路徑啟動的監看器出現變動列、監看任務結束，還是背景工作跑完，暫停等待的工作階段（AI 對話的執行單位）都會立刻恢復並由代理接手處理。對話閒置期間排隊等待的背景任務結果與監看事件，也會直接送達，不再乾等你的下一次按鍵。

問題修復

背景喚醒與執行中回合不再搶道或提早中斷

先前多個背景通知和進行中的回合交錯時，容易出現兩個回合同時並跑而擋掉壓縮檢查點，或是長任務才剛說完「接下來要做什麼」就突然停下來。現在背景任務完成喚醒代理時，會先妥善結束原本的等待回合，絕不另開第二回合並跑；回合輪詢中的長指令跑完後會繼續往下做，已結束的 shell 指令也不再阻礙長任務推進。 至於在回合尾聲進入等待的工作階段（AI 對話的執行單位），只要收到失敗的背景指令或剛進入等待前才抵達的跨對話訊息，就會正確喚醒而不再死停在 Working；但如果是該回合裡早已讀過的他方訊息，就不會再讓等待提前結束。

問題修復

補齊背景等待中斷、長輸出頭尾與卡住追蹤

背景等待出狀況或你想中途喊卡時，以前常找不到線索或被空白通知卡住倒帶。現在取消或插隊調整正在外部等待的執行流程，會直接走取消或取代出口而不報錯或照常恢復；空白的背景通知也不會再多生出無意義回合或擋住倒帶功能。 若代理在閒置時遺失喚醒訊號，阻塞解除後排程與背景喚醒會自動重新排隊；排隊背景工作啟動失敗則會寫進 /feedback 本機診斷與全螢幕外的終端機。代理查看執行中指令的過長輸出時，會同時拿到開頭、最新輸出與中間略過的位元組數。若背景通知持續遭拒醒，存檔也會記下是哪個阻擋鎖拒收以便追蹤，但含此紀錄的工作階段（AI 對話的執行單位）須更新程式才能開啟。

問題修復

Monitor 監看器保留最新輸出與真實停止原因

用 Monitor 監看背景流程時，以前中斷重連、當機或倒帶，常弄丟尾端畫面與停止原因。

機台黑盒子在斷電重開後留下最後讀數，超時或斷線停機也有紀錄，不再只見停機卻不知原因。

恢復工作階段（AI 對話的執行單位）的快照現在附上各 Monitor 最近輸出，恢復後馬上看得到，不再是空白。 監看器因雜訊、逾時或串流關閉而自停，會記下原因；遲來更新不蓋掉停止標籤，倒帶後也仍綁定原工作階段。當機恢復後，孤立的背景監看呼叫改標「Review … unresolved」並保留耗時。若監看器剛好在當機前結束，子代理先前回合中的該監看器會顯示自身記錄的結束狀態（ended、timed out 或失敗原因），而非 stopped。

問題修復

外部誤刪或調包對話紀錄檔時立即鎖定保護

有人或同步工具在 Muse 執行時刪除、替換或移走工作階段（AI 對話的執行單位）紀錄，以前可能讓它默默開新檔或寫進替代檔。

會計遇到帳本被調包會停筆示警；只有原本只是被移走，放回原處才可接續記帳。

紀錄遭刪除或替換時，Muse 會說明狀況、停止該工作階段儲存，拒收新訊息與設定變更；請重新執行 Muse，開新工作階段。協定回傳 session_log_lost，恢復或重連主機已載入的紀錄也會明確拒絕並給指引；其他對話遺失紀錄只影響那一支。若只是移走原檔，Muse 不會重建空檔，移回原處便能恢復儲存。待核准工具仍能收到「允許一次」「本工作階段允許」或「拒絕」並讓回合收尾；察覺紀錄遺失後，會儲存永久規則的選項則被拒絕並說明原因。

問題修復

對話紀錄遺失後各指令給出正確引導且互不牽連

紀錄遭外部刪除或替換後，操作指令不該讓你猜發生什麼事。重新命名、改權限或設定、發訊、/compact、/new、/clear、/fork、/side、倒帶與子代理操作，首次操作即說明紀錄遺失及處理方式；/export trajectory 改提示移回原檔，不再建議 --no-session-log。 側邊對話紀錄遺失不再擋住目前工作階段（AI 對話的執行單位）發訊、分支或新子代理；/resume 切入前也先拒絕，不打斷現有工作。離開遺失紀錄的對話時不再提示可恢復，已送達的 /goal 變更不再標成待送。訊號中斷 muse exec 時，退出不再追加第二個錯誤或宣稱日誌已刷新。若回合稍早儲存失敗，後續排隊訊息、模型、核准或推理力度變更遭拒，回合末的「session log flush degraded」警告也不再遺漏。

問題修復

對話檢視受損自動從日誌修復並消弭重載競態

當你恢復一個儲存畫面剛好毀損的對話時，程式以前常卡在重建錯誤直接罷工。

拼圖散亂後可以對照盒蓋原圖恢復畫面，現在也能依日誌恢復對話檢視，不再直接卡在重建錯誤。

現在恢復對話若遇上檢視資料受損，會自動從日誌修復；不支援重建的分支對話則立即回報 projectionRebuildFailed，健康狀態幀也會合併成最終狀態送出一次。 已載入對話若即時檢視失敗關閉，程式會透過註冊表的弱參照從日誌重新載入一次，失敗時只發報一次 projectionRebuildFailed；收到 healthy 訊號後，用戶端會重讀檢視、採納回合狀態，並跳過已繪製的列。先前在工具串流輸出或回合進行中重載容易撞車報錯的競態問題，也一併修好。

問題修復

當機重開後誠實標記未明工具狀態並支援跨版本接續

如果程式剛好在工具跑完或執行 ! 指令的瞬間當機，重開後以前常會直接寫成「成功」或留下一整格空白。

猶如停電前一刻遞出的簽收單，復電後帳本不會自作主張寫「已完成」，而是先蓋上「待確認」印章以免誤判。

現在當機前剛完成的工具呼叫，恢復後會標註為「unresolved」以示結果未確定；未完成的 ! 指令改標已取消並加註「可能已執行」，遇到未辨識狀態的恢復指令也不再誤顯示為成功，就算碰到沒記到結果的工具紀錄仍可顯示為未知並繼續對話。 由不同編譯版本儲存的工作階段（AI 對話的執行單位）重開後也能繼續收新提示而不報內部錯誤；但若新版於當機後自動恢復並告知代理曾被中斷，該筆對話須更新程式才能開啟。

問題修復

當機與停止背景指令後重開，不再擅自啟動回合

先前遭遇當機或在背景指令還沒跑完時退出程式，等你想起這段對話重新打開時，代理常常二話不說就自己開始回覆，把你剛開好的畫面打亂。

彷彿電腦從休眠醒來時先把沒處理完的文件留在桌上，等主人坐回桌前敲下第一句再動手，不會半夜自己開工。

現在從當機復原工作階段（AI 對話的執行單位）時，先前排隊的後續追蹤、背景結果與復原結果都會等你的下一則訊息，不再自行啟動回覆。一般重開則是不再為退出時被停止的背景指令擅自開回合；重開後的對話紀錄會將該指令顯示為背景執行中，不附帶完成列。

問題修復

當機後復原終端機迴響並讓待答問題準確作答一次

當 Muse 在工作階段（AI 對話的執行單位）進行到一半因磁碟寫滿等記憶體錯誤意外崩潰時，過去終端機會陷入「打字看不見字元」的無迴響狀態，非得手動輸入 reset 才能恢復，現在終止時會自動將終端機復原成正常顯示。 針對當機恢復後的待答問題，以前就算前面做過壓縮就答不進去、遇到滿佇列會被丟包、甚至同一題能連答兩次。現在就算早期內容已經壓縮過，當機前在等的提問依然能順利作答；遇到滿佇列時送出的答案會等佇列消化再送出，也不會再讓代理收到兩份重複答案。

問題修復

存檔記住核准與 3D 任務編號並修正舊版復原誤判

跨重啟或重開舊對話時，以前容易弄丟剛送出的請求狀態，或在連線用戶端上顯示假失敗與過期權限。現在存檔會記下正在套用中的核准與 3D 生成服務已受理的任務 ID，確保重啟後只結算一次或不因中斷遺失任務編號，但含這兩種新紀錄的對話須更新程式才能開啟。 重試重啟復原已捨棄的排隊回合時，會明確回報已捨棄而非看似還在排隊；遺失權限變更紀錄的對話，在恢復將重設時會先顯示重設後層級（無法決定或遭拒時則維持留存層級）。從連線用戶端首次開啟未曾壓縮或曾遇殘留重啟的舊工作階段（AI 對話的執行單位）時，也不再漏掉先前回合或誤報舊的 runtime_turn_task_lost。

問題修復

強化 `session-index.db` 抗損重建並止住無謂暴長

多個 muse serve 行程共用資料夾時，過去會反覆更新名稱清單、讓預寫日誌暴長；同時重建已刪除的 session-index.db（工作階段索引資料庫）也可能漏掉最初寫入。

多間分店共用總目錄，以前每隔幾秒就整本重抄、把紙塞爆，現在不再重複抄寫，損壞的目錄也能移開重編。

現在多行程並存不再反覆重寫名稱清單與撐大預寫日誌，訂閱清單變更的應用不再每隔幾秒收到假更新，兩個行程同時重建已刪索引也不會漏掉第一批寫入。 macOS 與 Linux 上的損壞索引會自動移開重建，讓 /resume 不必等手動刪檔。執行中把別的檔案移覆索引不再導致崩潰，也不會再顯示被換掉的舊索引檔裡的工作階段，但另一程式當下仍開著移入的新檔案時例外；移入更大的索引也不再誤判損毀。

問題修復

保住對話自訂名稱與超長首問不被清單漏掉

以前開過一場幫它取好名字的對話、或第一則訊息貼進好幾 MB 的除錯日誌，回頭打開 /resume 卻常發現名字被重取甚至整筆從清單裡消失。現在只要對話本身的歷史紀錄裡存著名稱，就算名稱清單遺失或在自動命名途中當機，下次開啟仍會沿用原本名稱，讓 muse resume <name> 繼續找得到。 同一台機器上就算同時跑著舊版程式，新版開啟的工作階段（AI 對話的執行單位）也不會再從清單憑空消失；第一句就貼上超大型提示的對話同樣會留在清單裡、可正常恢復並接續發問，標題則截取該提示的前 1,000 個字元顯示。

問題修復

模型目錄容錯與切換憑證後的清單更新

換了一組 API 金鑰、切換帳號，或是遇到後端模型目錄一時回傳空清單時，先前介面容易還卡在舊名單或直接罷工。

宛如換了會員卡進場或遇到菜單暫時空白，櫃檯不會直接趕人，而是刷新你的專屬選項並在無公開項目時先開出獲准的隱藏款。

現在重新啟動 muse serve 會確實改列新憑證可用的模型，清單也會過濾掉伺服器未提供的舊存模型；缺少輸出上限的目錄條目一樣會列出、保留上下文視窗做壓縮並套用標準輸出上限。 若目錄服務回傳零個模型，介面會明報抓取失敗而非悄悄清空清單；事先已指定模型的 muse exec 則印出通知照跑；連一個可見模型都沒有時，Muse 會改用授權給你的最新隱藏模型並在啟動通知點名，不再卡死在「model catalog has no visible models」。

問題修復

登入失敗、鎖住鑰匙圈與切換模型提示寫明解法

遠端登入 Mac 或帳號權限異常時，以前常被一句「API 金鑰無效」或內部代碼搞得一頭霧水，重試好幾輪才發現方向不對。現在在鑰匙圈上鎖的 Mac 上登入，會直接附帶鑰匙圈原生錯誤碼，提醒執行 security unlock-keychain 後重啟 Muse Code；若是因為應用遭停用被伺服器拒收登入，面板也會直說原因並提示重新登入無效。 對訂閱戶工作階段（AI 對話的執行單位）而言，登入後模型清單晚一步才到齊不再報「Model not found」；切換模型導致對話無法接續時，也會說明原因並引導開新工作階段就能帶著既有歷史繼續做，不再只丟下一句無法準備對話。

新功能

改進 /feedback 首次壓縮上傳與缺少金鑰提示

想在剛裝好程式、還沒連上遠端設定時就透過 /feedback 回報問題，或是回報一個龐大的長工作階段（AI 對話的執行單位）紀錄，現在比以前更順暢。/feedback 從首次啟動就能直接使用壓縮上傳，容納高達約 760 MiB 的工作階段紀錄，不必等抓取遠端設定。 若因紀錄太長而被迫縮減兩次才塞得進上傳額度，送出後的通知會精準顯示實際送出版本的保留與捨棄大小；當 /feedback 或 /bug 因缺少 Model API 金鑰無法上傳時，提示也會寫明兩種送出方式：設定一組 Model API 金鑰，或是 Meta 員工改用內部版 Muse。

問題修復

卡住的託管工作階段改在 30 秒退回可重試錯誤

透過 muse serve 操作一個已經卡死的工作階段（AI 對話的執行單位）時，過去送訊息、觸發技能或取消經常毫無音訊、吐出內部錯誤，甚至過一陣子自己偷跑。現在無論是傳文字訊息啟動或引導回合、跑技能或送出取消，只要工作階段卡住無法處理，都會在 30 秒後改回傳可重試的忙碌錯誤；忙碌逾時 30 秒仍未啟動的訊息也會撤回而不事後偷跑。 在操作順序上，允許第一次權限後於 shell 指令跳出第二次詢問時透過協定停掉回合，不再導致後續提示全報「approval replay failed」或卡死排隊；恢復對話後回答待辦結構化提問時，誤觸雜鍵也不會把你的 Enter 靜悄悄吞掉，暫存答案依舊只送出一次。

問題修復

排除工作階段重開、資料夾誤刪與重複報錯

進行工作階段（AI 對話的執行單位）的途中萬一工作區資料夾不小心被刪掉，以前接下來每呼叫一個工具都會連環報錯；現在只要重新呼叫工具就會自動復原，不會整場作廢。重開舊版存下來的對話時也重新保留了工作流程工具，遇到不支援的舊版工作流程格式時會改用新工作階段預設的版本，不必再另開新對話。 當兩輪連續遇到一模一樣的一般模型錯誤且中間沒有其他顯示內容時，執行期間也比照恢復後只顯示一次而不洗版；若是因為設定檔有誤導致啟動失敗，錯誤訊息除了指出問題設定，還會順手提醒修好設定後重新啟動 Muse。

問題修復

上下文壓縮用滿模型實際視窗並為失敗設停損

長對話聊到貼滿數十張全尺寸截圖、或接近模型容量上限時，先前壓縮會卡死在 512,000 token（AI 處理與計費的文字單位）上限，失敗後還每送一則訊息就花錢重算摘要。

好比打包快裝滿的行李箱，過去卡在固定大小且壓失敗還不斷重試，現在按真實容量計算，連卡兩次就先停手並說清佔位原因。

現在壓縮會用到模型真實上下文視窗，保留訊息已佔滿空間時不再白算摘要並點名原因；連續兩次壓縮或存檔失敗即暫停自動壓縮並顯示原因，直到重開或手動 /compact 成功為止。超窗自動重試會刪夠多舊訊以容納；無法判斷保留範圍且超限的回合則直接報「could not fit within the model's context window」；塞滿截圖的工作階段（AI 對話的執行單位）仍可恢復，過大停壓亦會明示。

問題修復

背景自動壓縮準時安裝且不再白做工或重複觸發

背景自動壓縮原本是為了不讓你乾等，但先前在 muse serve 裡碰到軟上限提前起跑的背景摘要，常因為撞上正在執行的回合就被丟掉，結果到硬上限還是得卡住等。

彷彿接力賽跑者在隊友衝線前就先把新接力棒備在線邊，過去撞上空檔就整支作廢，現在等這一圈跑完立刻遞上，下一圈直接接著衝。

現在內部回合或下一回合進行中完成的背景摘要，會留待回合結束再安裝；首回合補填工作階段（AI 對話的執行單位）名稱等背景細節不再拉低估計空間造成提早壓縮；剛完成壓縮或背景任務回覆後也不會再多跑一次多餘的自動壓縮；壓縮完後你送出的第一則新訊息更能正確接續該份摘要，不再重做摘要又漏掉最近一輪對話。

問題修復

修好 /compact 長對話凍結並持續顯示壓縮進度

壓縮檢查點瘦身，避免數千輪後膨脹到存不進去

用 muse exec 反覆接續同一個工作階段（AI 對話的執行單位）跑自動化腳本時，對話拉長到幾千次提問後常會突然寫檔失敗、卡在半途。

壓縮對話的預覽與往上翻頁一致停在摘要分隔線

看壓縮過的長對話時，/resume 預覽與實際內容曾對不起來，往回翻頁也可能翻出壓縮前的舊紀錄。

小說前幾章已收成前情提要，翻到書籤就該停下，不再把收起的草稿整疊拉出。

現在恢復預覽會顯示開啟後同樣的近期對話；透過工作階段（AI 對話的執行單位）協定往回翻，會停在單一早期對話摘要，更早的游標會回報檢視已截斷。 一般舊版壓縮工作階段要先讀取，翻頁才會停在摘要；新回合後仍可能顯示舊歷史，須再次讀取。muse serve 則已修好更多情境：檢視重建後從第一頁就停在摘要；舊版壓縮對話讀取後新增回合仍會停住，恢復後在第一頁前新增回合也一樣，即使伺服器啟動後從未恢復或讀取過也能停在摘要。

問題修復

託管檢視落後或損毀時自動從壓縮點重建並消除假警告

透過 muse serve 開啟存檔檢視落後、無法讀取或只剩結尾標記的壓縮對話時，以前常得重讀整份長日誌甚至開不起來。現在 muse serve 會在下次開啟時直接從最新壓縮點重建檢視，把先前內容收進「earlier conversation restored from checkpoint」分隔線後，壓縮點前缺損的紀錄不再阻礙開啟，就算壓縮點之後的紀錄也受損，仍會從最新一則訊息開聊。 舊版經定期歷史檢查點精簡或略過壓縮的對話，往回翻頁時一樣會在早期摘要處停下；成功執行一次或兩次以上 /compact 後恢復工作階段（AI 對話的執行單位），也不再誤跳中斷通知或「runtime closed before context compaction completed」假警告。

問題修復

收回最後一回合後，壓縮與恢復不再重現舊訊息

剛存好進度就抽回上一輪發問時，以前重開或分支可能無法載入，甚至又看見已收回的內容。最後一回合先儲存檢查點但未壓縮，之後又被收回，恢復或分支現在會從前次壓縮接續，不再拒絕載入或重播全部日誌；舊版存檔在同樣條件下恢復也適用。恢復最後一回合已收回的壓縮對話，會顯示最近一次壓縮之後的內容，不再重播整份日誌或顯示被收回回合的摘要。透過工作階段（AI 對話的執行單位）協定重讀或恢復壓縮對話，也不再保留已收回回合帶回的舊訊息。若最新壓縮屬於已收回回合，讀取仍會被拒絕；從早期歷史呼叫 view/subscribe 也回同樣錯誤，不再給出原地打轉的游標。

問題修復

檢查點出現缺漏或損毀紀錄時，盡力救回並引導匯出

遭遇異常斷線讓壓縮紀錄殘缺不全時，以前常整段對話直接死鎖、一條錯誤訊息卡死再也進不去。傳送或恢復工作階段（AI 對話的執行單位）時，不再因「projection failed: tool-result clear entry did not match」而失敗。起因是某筆「tool-result clear」清理紀錄找不到對應結果，或對應到不只一個結果；程式現在會略過壞掉的那筆，保留舊輸出繼續。 壓縮中途斷掉留下一大疊殘餘紀錄，重開時也不再因此失敗；若檢查點上方有紀錄遺失，恢復後會把權限重設回預設值並跳出警告，讓你仍能打開對話而非被鎖在門外。唯一例外是當最新檢查點屬於已取消的回合時，為免錯載更早歷史，程式會明確拒絕恢復、讀取或分支，並引導改用 muse export 救回日誌。

問題修復

壓縮對話重開後保留圖片提問且不重跑舊佇列

以前在壓縮過的對話裡重開視窗或貼上截圖繼續問問題，常發生兩個意外：要嘛已經跑完的排隊舊訊息莫名再執行一次，要嘛剛發的圖片提問剛好撞上回合開頭壓縮而被丟掉，結果代理跑去回答上一題。現在重開壓縮工作階段（AI 對話的執行單位）後，已完成的排隊訊息不會再重跑；夾帶圖片的提問在回合開頭觸發壓縮時也不會遺失，代理會確實回答該張圖片的問題。重開後才補送的圖片提問，在下次再重開時亦能繼續留在模型上下文裡並支援 /compact，只是暫時還不能倒帶或從該回合開分支。

問題修復

修好分支對話重開、檢查點起跑與卡片顯示

把一段長對話開出分支或側邊討論來做實驗，以前重開分支後常得每輪重讀全部歷史，遇上舊紀錄破損、日誌重播錯誤或 "invalid_target" 就整支打不開，甚至要退出時還跳出還有工作在跑的假警告。現在分支本身壓縮過後，重開與再開子分支／側邊對話都會直接從最新檢查點起跑而不受舊紀錄損傷阻礙；補追存過檢查點的對話開分支與側邊對話也不再報 "invalid_target"。 恢復分支工作階段（AI 對話的執行單位）時，日誌重播錯誤與退出時的假工作警告都已消除，先前執行過的指令也會維持收合整齊的「Ran commands」卡片，不再炸出整頁原始輸出。

分支對話支援倒帶，並釐清壓縮邊界與讀圖失敗提示

輸入框保留草稿、支援運行中回捲與 Cmd+V 貼圖

字打到一半按上鍵想翻找前面問過的句子來改，以前整段辛苦打好的草稿直接飛走；想在 VS Code 或 Cursor 裡按 Cmd+V 貼截圖也沒反應。現在編輯按上鍵叫出的歷史提示時，旁邊會顯示 · edited，按 Esc 或下鍵就能把還沒送出的原草稿叫回來；macOS 用戶在發送空白貼上訊號的終端機裡按 Cmd+V 也可順利附上截圖。 工作階段（AI 對話的執行單位）執行期間用滑鼠滾輪或觸控板回捲歷史已恢復正常，點擊輸入框不再跳移游標。當機重啟後，當機前排隊的訊息會照送出順序各跑一次再輪到新訊息，訊息更新失敗時佇列輸入面板也不再誤報「your input still works」。

問題修復

終端機程式狀態準確顯示運作與待答，計畫列不遮狀態

如果你用的是支援顯示程式狀態（OSC 7501）的終端機，以前在壓縮對話、跑排程、整理回顧或剛被背景任務叫醒時，程式狀態卻還顯示已完成，代理打字問你問題時也看不出它在等你回話。

就像錄音室門外的燈號必須照真實狀況亮起，「作業中」與「等嘉賓回答」分得清清楚楚，房間變窄時儀表燈也不會被牆板擋住。

現在不論是背景喚醒、排程、上下文壓縮、啟動回合或產生回顧期間，都會正確顯示運作中；若回合以純文字提問作結，即便發生在訊息確認前的快速回合，也會立刻亮成等待你回覆。在較矮的終端機執行回合時，計畫面板還會自動摺疊成較少列數，留住開啟 HUD token（AI 處理與計費的文字單位）欄位時的即時用量列。

問題修復

窄窗保留對話末行、Hook 通知不洗版並互通舊版紀錄

把終端機窗格縮到只剩 5 或 6 列高時，以前回合一結束畫面看起來就像全空白，對話紀錄也常被各種 hook（特定事件觸發的小程式）訊息洗版，或是桌面版看不到終端機上還開著的舊對話的歷史，只顯示空白。現在就算在只有 5、6 列的窄窗格裡，助手回覆與對話最後一行也會緊貼在輸入區上方顯示而不像剛開的新工作階段（AI 對話的執行單位）。 hook 訊息不再塞進對話紀錄列，改為簡短的狀態通知，右下角顯示重要阻擋、失敗或逾時警告的 5 秒內，其他 hook 訊息也不會將它蓋掉。桌面版現在能正常讀取終端機上 Muse Code 1.4.9 至 1.4.14 仍開啟中的對話歷史；由舊版佔用的 muse serve 對話即使日誌曾有無法讀取的區段，仍可顯示已存歷史。

問題修復

動手改檔、清資料夾與更新任務前先停步說清楚

請 AI 規劃改動、清理目錄或處理共享任務時，最怕它擅自刪過頭或用長篇計畫洗版。

想像請師傅來大掃除，他會先列清單問你陌生箱子留不留、遞上計畫便條，等你點頭才真的開工。

現在擬完計畫會用白話交代尚未修改任何檔案，提示可回 go 開始或告知調整處；要求將計畫存檔時會存在指定或專案顯眼位置，只回傳連結、一行結論與關鍵決策。 清理目錄時會先列清單、只刪任務項目，遇到疑似無關的另一儲存庫、符號連結（捷徑檔）或資料會先詢問，未獲回覆便保留並於結尾交代已刪與待確認項目。你口述的已發生遷移或部署，代理會直接採納、改掉舊預設並在後續回合記住。任務本身的文字或代理提示要求它更新共享任務的狀態、計畫或欄位時，Muse 不會照辦；它先做你要求的事，再問你要不要更新，等你同意才改。

看懂圖片真實像素尺寸，手機直拍縮圖不再歪斜

把螢幕全圖或手機拍的照片丟給 AI 幫忙檢查排版、報出按鈕座標時，以前傳過協定常縮小失敗、方向橫躺，甚至報出對不上的像素座標。

好似送相館縮印海報，店員不只先把橫躺的照片轉正，還附註原圖的長寬像素比例，量座標才不會算偏。

彷彿修車師傅排查異音，不只檢查零件有沒有裝上去，而是實際沿著車主開過的路段跑一圈，順手把相鄰路況一起測過才交車。

加快 3D 網頁與瀏覽器遊戲開發自測流程

用一兩句話請 Muse 試寫互動立體頁面，或丟給它長篇企劃做網頁小遊戲時，以前就算需求很單純也得跑完多輪審查，本機沒裝檢視工具更會直接跳過驗證。

彷彿修補一本原本用線裝直排印製的古書，師傅不會擅自換成橫排膠裝，在當地問路也改講當地慣用的路標名稱。

緊扣你的要求回答，不縮水需求、不夾雜外語也不硬繞禁令

裝了一大堆擴充技能或用自訂代理跑長任務時，以前常因為工具名字對不上而呼叫錯對象，或者技能提醒硬把代理導去另一個重複功能的技能。現在無論是用斜線指令啟動的內建技能（在終端機包含 --no-session-log 的所有工作階段皆適用），還是由自訂代理預先載入的內建技能，裡面的工具名稱都會對齊當下提供給模型的名稱。 當安裝的技能多到目錄裝不下時，內建技能與提示中點名的技能會優先保留完整說明，讓出其餘技能的空間；若已載入的技能已涵蓋同一步驟，技能提醒也不再硬導向別的技能。定義中宣告了記憶功能的子代理也不再中途因記憶錯誤停擺，歷史壓縮時更會保存上下文好讓重開維持流暢。

換成在分店廚房做菜，廚師不只盯緊最新點單，食材與食譜也只從這間分店的架上拿，不再跑回總店或往走廊亂放東西。

消除閒置 CPU 飆高，恢復長對話不再重開整排執行緒

猶如麵包店早晨開門只把新鮮出爐的那幾盤擺上檯面，不再把冷庫裡整批陳年麵團全搬出來，也不再反覆猛推早已上鎖的儲藏室門。

現在遇到日誌已消失的已結束子代理等無法讀取的背景任務，TUI 會停止每秒重試好幾次，閒置對話不再吃滿一顆 CPU 核心；新舊版並存時也不會再彼此反覆重建對方的已存工作階段清單。 恢復無檢查點的長對話不再為每個已結束 shell 指令各開一條背景執行緒，降低啟動工作量與記憶體隨指令史膨脹；恢復畫面也只顯示符合終端機回捲緩衝的最新段落並加註先前內容未顯示，不再讓整份歷史洗過螢幕。

猶如盤點厚重卷宗時改為逐行翻閱、一次只搬一箱進來核對，不再把所有大箱子同時攤開佔滿整張工作桌。

現在更新後重建工作階段清單不再同時讀取多個大型工作階段，有效壓低尖峰記憶體用量。 長時運行的對話在背景重新整理過去大型工作階段的索引時，包含沒有儲存檢查點的舊大型對話，佔用的記憶體都變得更少；往回翻頁瀏覽長對話保留的歷史紀錄時，也改成邊讀邊逐行解碼，不再先將整份日誌檔案一股腦塞進記憶體裡才開始解碼。

新功能

重複模型指令只存一份，執行步驟也更省記憶體

一個對話跑了上百個回合之後，每一輪其實都夾帶著一模一樣的模型指令與上下文設定，過去程式就像每回合都重新影印一份塞進記憶體裡。

好似班級發講義時把每堂課一模一樣的規則只貼一張在黑板旁，不再每一節課都重印一百份發進抽屜裡佔空間。

現在長對話不論是在運作過程中、還是恢復舊版程式錄下來的歷史紀錄，只要各回合或各次執行之間沒有變動的模型指令與上下文設定，記憶體裡都只保留一份。 紀錄裡的每一個執行步驟在記憶體中所佔空間也一併縮小，讓長時間進行的工作階段（AI 對話的執行單位）更省資源。

減少日誌備用緩衝與磁碟刷新，加快批次開新對話

新功能

已結束子代理對話讀後卸載，工作流程檢視縮減紀錄

一場長工作階段（AI 對話的執行單位）裡跑過好幾輪工作流程與幾十位子代理後，以前哪怕它們早早收工或失敗結束，整個對話內容依然硬生生卡在記憶體裡。

現在讀取已結束子代理的任務狀態，不會把整段對話一直留在記憶體中；已結束子代理的對話在最後讀取後會卸載，工作流程中失敗或未交結果的子代理，則在工作流程讀完其結局後卸載。 恢復長對話時子代理檢視不再另存一份所有歷史事件，工作流程檢視也改成只記下每位代理的工具呼叫與 token（AI 處理與計費的文字單位）用量，不再背著整段執行紀錄不放。

新功能

大量指令輸出與執行紀錄由多份改存單份，省下重複記憶體

跑編譯或測試指令吐出滿螢幕的結果、或開過一大堆子代理與工作流程時，以前同一段指令輸出竟然會在記憶體裡存成三份，已結束背景任務的最近輸出也存兩份。現在 Muse Code 把大量指令輸出從三份減為只留一份，已結束背景任務的最近輸出與恢復長對話裡保留的執行事件亦各只存一份（不再同時存在執行歷史與模型上下文檢視）。 工作階段（AI 對話的執行單位）開著且跑過子代理或工作流程時，沒用到第二份准入紀錄不再保留，每個小型任務紀錄清單也只維持實際使用的槽位不預佔空位，帶壓縮檢查點恢復的工作階段整體記憶體佔用也跟著下降。

新功能

長時間運行的 `muse serve` 在對話離開後即時釋放記憶體

如果把 muse serve 當成常駐服務開著好幾天、陸續接待過幾十上百場工作階段（AI 對話的執行單位），以前即便用戶端早早離開，記憶體還是會隨著服務過的場數一路往上升。

現在一旦工作階段被離開或卸載，muse serve 就會把對應記憶體徹底釋放；每個已載入但閒置的工作階段消耗的 CPU 更低，就算同時掛著許多工作階段，新開對話的成本依然很輕。對單純重開的長對話而言，恢復過程的尖峰與後續開著掛在背景的常駐記憶體也一併壓低。

When asking AI to debug or inspect existing code, it used to test only the exact failing input, accidentally delete code that was already right, or stop after checking config files when you reported a change had no effect.

Mechanics tracking down a rattle do not just check whether a part is bolted on—they drive the exact route the owner took and test neighboring road conditions before handing back the keys.

Now bug fixes get a focused failing test for each reported defect, along with regression tests covering another position or order, extreme boundary values, and input rules restated in the request that the fix claims to handle (still without introducing new test frameworks or running the full suite unnecessarily). When checking existing code, it fixes only what is wrong and explains why correct behavior is kept; when you report that a change does not show up, it traces the code path you actually ran; the verify observer can now see passing results at the end of long tool outputs to reduce needless re-verification; and fix and build summaries weave closely related facts into connected sentences instead of splitting one fact per line.

FEATURE

Speed up self-testing for 3D web pages and browser games

When asking Muse in a sentence or two to prototype an interactive 3D page or handing it a long design document for a browser mini-game, even simple requests used to go through multiple review rounds, and missing local viewing tools caused it to skip verification altogether.

Game studios testing a prototype do not wait for every art texture to be finished before playtesting—once the engine runs, they let a tester check the feel and have two review rounds test the same build in parallel to polish it faster.

Now, when a machine has no browser, Muse installs a headless browser (a mode that runs without a visual interface) via the system package manager to inspect the 3D page itself, stating plainly that it could not run only if that install fails. Short one- or two-sentence 3D web requests take a single light pass covering a desktop run, one input test, a fix, and a final check, while detailed briefs still go through every check. The built-in browser-game skill also lets the first critic playtest as soon as the game runs before art is added, while the second and third critic rounds test the same copy simultaneously.

BUGFIX

Give direct paths and start commands when opening built pages or games

When a web page or browser mini-game was ready to view on your own computer, the agent used to ask what you wanted to do, promise to keep a server running only to shut it down on exit, or secretly spin up a hidden background server.

Carpenters finishing a market cart hand you the address and startup slip, state honestly that the lights go out when they clock off, and neither light a hidden fire nor promise to watch over it.

Now, after building a browser game on a remote machine, Muse hands off a local URL you can open from your own computer along with an SSH tunnel command; on a Mac, asking for a page link immediately gives the file path or start command without going back to start a hidden background server. If you ask it to keep a server running, it says plainly that it cannot keep it alive after quitting and provides the command to start it yourself, and if it starts a server on the spot, it notes clearly that the server stops when Muse quits.

FEATURE

Keep CRLF line endings in Windows edits and rewrite PowerShell commands

Two of the most frustrating parts of developing on Windows are AI spitting out grep and export commands that PowerShell does not understand, and rewriting all line endings to Unix format after an edit to create piles of noisy diffs.

Bookbinders repairing a thread-stitched vertical volume do not arbitrarily rebind it as a horizontal paperback, and when asking for directions locally they use the local landmark names.

Now on Windows, Muse guides the agent to write native PowerShell commands such as Select-String and $env:NAME = .... When reading a file with Windows (CRLF) line endings, it also reminds the agent not to switch the line endings; when editing CRLF files directly, plain line breaks match multi-line text properly and preserve CRLF in the replacement, and if an edit fails only because of line endings, it says so clearly.

FEATURE

Follow requests closely without shrinking scope, mixing languages, or bypassing blocks

The biggest headaches with an AI assistant are having it stop when you send a mid-task note, hide things when you ask it to simplify, or suddenly switch languages mid-sentence.

Personal shoppers working from a checklist answer direct questions first, report immediately when they hit a gate that requires your own ID, and never quietly downsize the order or switch to another language.

Now Muse answers direct questions first, keeps working when you send a message mid-task, does not stop while requested changes remain unmade, asks for help right away when blocked by a login only you can complete, stops working around blocked downloads or package indexes that fail certificate checks, and actually removes extras instead of hiding them when asked to simplify. The recommended option in clarifying questions keeps the full scope, and requests with settled outcomes proceed directly; interrupted unanswered questions are asked again before building on them. Progress text that switches into another script is retried once, and commentary or tool text that flips into French, Spanish, or Indonesian during English sessions is resampled as well. If a reminder keeps a turn thinking after its answer and you press Esc to stop it, Interrupted appears under the answer.

FEATURE

Align Skill Tool Names and Catalog Priority, Keep Memory Subagents Running

When you have many extension skills installed or run long tasks with custom agents, mismatched tool names used to cause calls to the wrong target, or skill reminders would push an agent toward another skill with overlapping functionality. Now, whether a built-in skill is started with a slash command (including every session in the terminal app started with --no-session-log) or preloaded by a custom agent, the tool names inside it match the names currently offered to the model. When more skills are installed than the catalog can fit, built-in skills and skills named in the prompt keep their full descriptions first while other skills are trimmed to make room, and skill reminders no longer steer the agent to a different skill if an already loaded skill covers the same step. A subagent whose definition declares memory also no longer stalls partway through with a memory error, and it saves its context during history compaction so reopening it stays smooth.

BUGFIX

Faster Long-Chat Sends, Folder Boundaries, and Accurate Worktree Config Loading

When you press Enter to send a message in a long chat with many skills installed, or experiment with changes in a worktree (a feature for opening multiple parallel copies of the same project), sending each prompt used to stall for a while and to-do suggestions often contradicted your latest request.

Cooking in a branch kitchen works the same way: the chef watches only the latest ticket and pulls ingredients and recipes strictly from that branch's shelves instead of running back to headquarters or leaving things in the hallway.

Now the setup work before each message in a long chat no longer repeats for every installed skill, so pressing Enter sends nearly as fast as a fresh chat, and skill, memory, and to-do suggestions in long turns stay aligned with your latest instruction instead of suggesting tests when you only asked for an explanation. When you tell the agent to stay inside a designated folder, it keeps its throwaway test scripts there instead of writing them to /tmp. In a worktree session, Muse loads project skills and rules from the copy itself. Local hooks (small programs triggered by specific events) and skill files there also load and take effect properly.

FEATURE

Enterprise Certificate Chain Support, Full Long-Line Reads, and Parallel Hooks

Behind a corporate proxy, on an NFSv3 network mount, or when reading data files minified onto a single long line, telemetry verification used to fail, chat history could become unreadable after a restart, or long lines were cut short. Now usage telemetry trusts the certificate file of the certificate authority (an organization that issues connection identity certificates) specified in telemetry.ca_bundle. When a company re-signs TLS-encrypted traffic, telemetry can verify the connection and keep working, and muse serve chat history stored on an NFSv3 mount remains readable after a restart. When reading extra-long text lines in a file, the full line is read as long as it fits within the output limit, with byte-range guidance provided if it exceeds the limit. Parallel tool calls now launch their own hooks simultaneously without waiting on each other, and Muse Spark 1.3 at max reasoning effort receives the same complete answer-style and grounding guidance as other models.

FEATURE

Eliminate Idle CPU Spikes and Stop Spawning Threads on Long-Session Resume

When several terminal windows sat idle or different versions of Muse Code ran side by side, fans used to spin up for no clear reason, and resuming a long session without a checkpoint meant waiting for old history to scroll across the screen.

Bakers opening a shop at dawn put only the fresh trays on the counter rather than hauling out every batch of stale dough from the freezer or repeatedly shoving a locked pantry door.

Now, when a background task can no longer be read—such as a finished subagent whose log is gone—the TUI stops retrying several times a second so idle sessions no longer peg a CPU core, and running old and new versions together no longer causes them to repeatedly rebuild each other's saved-session list. Resuming a long session without a checkpoint no longer opens a separate background thread for every finished shell command, reducing startup work and keeping memory from growing with command history, and the resumed view displays only the newest portion that fits the terminal's scrollback buffer with a note that earlier conversation is not shown instead of flooding the screen with the entire history.

FEATURE

Lower Memory Use When Rebuilding Session Lists and Paging Long Chats

Whenever you opened the app right after an update, or when the session list rescanned large accumulated chat logs in the background, memory usage used to spike.

Auditors checking thick case files read them line by line and bring in one box at a time instead of spreading every heavy crate across the entire desk at once.

Now rebuilding the session list after an update no longer reads multiple large sessions at the same time, cutting peak memory usage. Long-running chats use less memory when refreshing the index of large past sessions in the background, including old large sessions without saved checkpoints, and paging back through a long session's retained history now decodes each line as it is read instead of loading the entire log file into memory first.

FEATURE

Store Repeated Model Instructions Once and Slim Down Run Steps in Memory

After a chat runs for hundreds of turns, every turn carries the exact same model instructions and context settings, and the app used to behave like it photocopied them into memory every single round.

Teachers handing out class rules post one copy beside the chalkboard instead of photocopying a hundred identical sheets for every desk each period.

Now, whether a long chat is actively running or resuming history recorded by an older version, model instructions and context settings that stay unchanged across turns or runs are kept in memory only once. Each recorded run step also takes up less space in memory, making long-running sessions lighter on resources.

FEATURE

Remove Duplicate Session-Log Copies to Cut Resume and Growth Memory

Previously, resuming a long session or continuing a conversation kept an extra duplicate copy in memory, even storing every old and new log record twice just to verify its original bytes. Now background-task and subagent records read back from the session log are no longer stored twice, and each line of a long session without a checkpoint is no longer held twice while loading, sharply reducing peak memory during resume. For both resuming and subsequent writes, log records no longer keep a second copy to prove their original bytes, and the task and run state kept for later appends no longer duplicates records the session already holds, so memory grows more slowly over long chats.

FEATURE

Trim Log Spare Buffers and Disk Flushes to Speed Up Batch Session Creation

When launching a batch of new sessions at once or reopening a long chat, the internals used to reserve oversized spare buffers, duplicate queued messages and event indexes, and flush to disk frequently during creation. Now, when bursts of new session requests arrive through muse serve, writing to the scheduled-task store performs fewer disk flushes so creation finishes sooner. When resuming a long chat, the live session log no longer holds an extra spare buffer sized for every record, and the replay check kept for later checkpoints no longer stores a copy of every queued message; the index that matches recorded copies of run and approval events also keeps each copy only once, keeping memory light during long runs.

FEATURE

Unload Finished Subagent Chats After Reading and Trim Workflow Views

After a long session ran multiple workflows and dozens of subagents, their entire conversations used to stay stuck in memory even after they finished or failed.

Contractors wrapping up a project leave behind only the tool and expense breakdown when they walk out, rather than keeping the whole crew seated in the conference room.

Now reading a finished subagent's task state no longer keeps its whole conversation in memory; finished subagent conversations are unloaded after they are last read, and subagents in a workflow that fail or end without a result are unloaded once the workflow reads their outcome. When resuming a long chat, the subagent view no longer keeps its own copy of all past events, and the workflow view now records only each agent's tool calls and token (the text unit AI processes and bills by) usage instead of holding onto the entire run.

FEATURE

Keep Large Command Output and Run Events Once Instead of Multiple Copies

When build or test commands poured output across the screen, or after spawning many subagents and workflows, the same command output used to be stored three times in memory, and recent output from finished background tasks was stored twice. Now Muse Code cuts large command output from three copies down to one, and both recent output from finished background tasks and kept run events in resumed long chats are stored only once (instead of living in both the run history and the model context view). While a session is open after running subagents or workflows, an unused second copy of their admission records is no longer kept, each small per-task record list keeps only the slots it actually uses without pre-allocating empty ones, and resumed sessions with compaction checkpoints use less overall memory.

FEATURE

Long-running `muse serve` immediately frees memory after a session is left

If muse serve stayed running as a persistent service for days, serving dozens or hundreds of sessions (units of AI conversation), memory used to keep climbing with the number of sessions served even when clients left early.

Train station lockers pop open and reset as soon as travelers pick up their items, and attendants no longer have to keep checking idle lockers, so the whole station can sustain long-term operation.

Now, as soon as a session is left or unloaded, muse serve fully frees its memory; each loaded but idle session consumes less CPU, and starting a new session stays lightweight even with many sessions loaded at once. For a long session that is simply resumed, both peak memory during recovery and resident memory while it stays open in the background are lowered as well.
