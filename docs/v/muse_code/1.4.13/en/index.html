Muse Code 1.4.13

Released: 2026-10-25

Release notes

BUGFIX

Filesystem Deny Rules Supported on macOS and Linux to Strictly Block Sensitive Path Access

When you extend :ask-me in a permission profile with filesystem deny rules, the system now enforces them on macOS and Linux. Whether using workspace-root deny globs (such as **/*.pem) or absolute and home directory ~/ deny rules, matching read and write requests are directly refused, and sandboxed shell access to matching paths that exist when each shell command starts is blocked.

Just as a vault card reader secures restricted areas, where guards were previously only told to keep watch verbally, the card reader now actively locks down blacklisted zones and sounds an alarm whenever unauthorized personnel touch the sensor.

On Linux, files created mid-command under a deny glob are not covered. macOS prevents them live through Seatbelt regex (syntax for matching text patterns with symbols) with no snapshot window. Denies on not-yet-existing paths are masked at their first missing component, while the profile keeps its write grants elsewhere.

FEATURE

Standalone Subscription Allowance Queries Supported with Proactive Warnings Near Limits

If you want to check your remaining model usage, you can now check it directly without sending a message to run a model turn. Running muse usage displays your subscription allowance (including window, weekly use, reset times, and tier). When a run sees no new usage updates, muse exec --json reads that information as well.

Think of opening your mobile carrier billing page on your phone at any time: instead of having to place a call to see remaining data on your bill, you can now open the panel and check your balance directly.

When you are near your usage limit, a warning appears above the message queue showing your remaining allowance and reset time. If execution stops due to a usage limit, the interface clearly explains when you can continue asking questions, and denied requests retain full error details for troubleshooting.

FEATURE

Built-In Visual Coding Skill Guides Triage as 3D Game Pipeline Posts Steps to Todo List

When you ask an agent to build a 3D page, a browser game, or handle a Blender project, the built-in visual-coding skill now actively directs the agent to the single built-in skill responsible for that domain before writing any code, preventing one request from launching two competing build processes.

Picture a hospital triage desk directing incoming patients to designated specialty rooms based on symptoms, stopping two departments from competing to treat the same patient.

For the /game-3d-visuals command, execution is now split into three sequential steps: planning, building, and reviewing, posting a one-line result to the todo list after each step finishes. The skill also explicitly names each pipeline run, so its first launch is no longer refused or forced to retry.

BUGFIX

YOLO Mode Retains Question Tool and Supports Async Inquiries to Confirm Requirements

When using the --yolo flag to let tools execute tasks automatically, you often want to save confirmation steps without missing important decisions. The --yolo flag no longer withholds questions completely; instead, it keeps the request_user_input question tool and enables an async questioning mechanism, allowing the agent to ask essential questions while running in the background.

Like an autonomous delivery truck driving smoothly on its own, it can post an async notification on the dashboard for your confirmation whenever a delivery address is unclear, rather than stalling out in the middle of the road.

If you prefer the execution process to run entirely uninterrupted without asking anything, pass --disable-request-user-input to disable questions completely.

BUGFIX

Strict Isolation for Untrusted Workspaces with Proactive Reset on Server Permission Anomalies

When opening project folders from unknown sources, security settings draw a stricter boundary. Sessions in untrusted workspaces no longer receive project rules recorded by earlier trusted sessions. Session worktree (Git's feature for running multiple parallel copies of the same project) recovery now enforces the same protected paths. Hosted sessions in untrusted workspaces no longer run workspace status checks or Sapling snapshots, refusing to continue if trust is never established.

A visitor no longer inherits access keys left behind by a predecessor, and missing log entries also prevent old keys from granting admission.

When muse serve resumes, forks, or opens a side chat from history that lost a permission change, it no longer reopens with older, wider permissions: it resets to defaults, keeps your saved settings when they were stricter, or switches to read-only when the two cannot be safely combined. Prior approvals for "allow for this session" given before the loss stop applying. A permission profile chosen when resuming applies after the reset, or replaces the reset when resetting is not allowed. When no safe reset exists or managed policy forbids it, the chat refuses to open and asks you to start a new chat.

FEATURE

Forked Chats Continue Through Disk Write Failures and Skip Abnormal Turns on Reopen

Creating a forked chat in low-disk-space environments no longer blocks the entire flow if the start of one of its turns cannot be written to disk. Such forked chats continue working normally after compacting and reopening, saving checkpoints again upon restart. Loading them in an application or another client no longer blocks subsequent checkpoints, allowing forks from compacted chats to continue smoothly.

When a commuter train encounters a damaged carriage door lock, station staff clear that carriage and make a single announcement before departure, while the rest of the train keeps running on schedule.

The system leaves unwritten turns out of the record and reminds you once per reopen, ensuring the chat can proceed without interruption.

BUGFIX

Automatic Recovery from Full Disks or Interrupted Storage Resumes Progress Immediately

Sessions now feature more resilient self-recovery when encountering temporary storage access errors. If saving a tool result fails due to a full disk or similar issue, the chat can still compact immediately; after a restart, that turn is preserved with the result marked as lost instead of disappearing. When reading a chat file is blocked by a brief I/O error, the chat resumes saving progress once the read succeeds, without requiring a restart. Compaction checkpoints continue working without a chat restart even if saving a subagent message or background record fails due to lack of disk space. When a brief disk error occurs mid-task or interrupts a background save, progress saving resumes at the next checkpoint once the error clears, covering side chats and records already written to disk. While disk writes keep failing, the system also reduces repeated session-log bookkeeping to avoid consuming resources.

BUGFIX

Long-Running Goals and Chat Compactions Save Reliably with Warnings on Cleanup Failures

When executing complex tasks over long durations, the saving mechanism for chat history and checkpoints maintains a steady cadence. Long /goal sessions reliably save resume checkpoints again, keeping content compact and restoring quickly instead of slowing down after every compaction. After a chat messages a subagent and runs multiple tools at once, subsequent checkpoints no longer stop saving. Prompts formatted like session-message envelopes also no longer prevent future sessions from saving resume checkpoints. Automatic compaction no longer loses Monitor messages when a model response ends early. Triggering compaction while a background task save remains unconfirmed still saves checkpoints, keeping older history until the background save resolves instead of skipping the save. If cleanup after a finished turn keeps failing (such as goal accounting or live turn state), the chat displays one warning naming the failed item right after that turn, or the next time you open the chat if you have moved on to another turn. If the warning itself cannot be saved, it appears only while you remain on that turn.

BUGFIX

Background Workflows Retain Todo Lists with Clearer Stopping and Pausing Reports

When letting an agent run long-running tasks in the background, you get clearer visibility into the real-time status of each process. After launching a background workflow, the todo list remains on screen while the workflow runs, rather than disappearing as soon as the turn that triggered it ends. When you manually stop an operation, the stopping message clearly indicates whether a workflow or a background command was stopped.

Much like a central assembly dashboard in a factory, progress remains visible on screen even when operators switch views, and pressing an emergency stop clarifies whether the conveyor belt or the inspection station was paused.

If you pause a workflow right after it finishes, the interface directly reports that it has completed and displays the execution result, avoiding getting stuck in a paused state with no result. When using session/leave with stop: true, if a workflow cannot be stopped due to a conflicting stop record, the leave fails and the session remains with its host. As a known limitation, such leaves continue to fail even when retried with a new command id, until the host process restarts.

BUGFIX

Subagent Communication Preserves Plain Summaries as Unqueue and Peer Timelines Function Normally

In multi-agent collaborative environments, message routing and queue scheduling are organized more cleanly. Notes sent to a subagent over a remote session preserve their plain summary rather than losing their original appearance. When a subagent is busy handling other tasks, waiting notes clearly show Queued rows to facilitate tracking dispatch status.

In an office handover board, notes assigned to an assistant stay neatly in the queue column with their original takeaways intact, and pending messages can be pulled back at any time.

When revoking a queued message using turn/unqueue, the cancellation succeeds even if the message waits behind an internal turn, instead of incorrectly failing with missing_run and running the message anyway. After a session accepts a message automatically, the peer message timeline also displays normally, without showing an unavailable error.

FEATURE

Desktop Syncs Third-Party Models, Restoring Session Names and Reducing Memory

When switching between different interfaces, the model menu and session list now provide a consistent experience. Desktop and other connected clients now offer the exact same third-party model options as the terminal model picker. Session names you customized earlier show up again in the list and can directly resume conversations with muse resume <name>, read from each session's own history.

Following a lightweight catalog index design, display shelves only present item names and item numbers without stacking the entire inventory stock in the aisles.

Starting the app or muse serve while other sessions are running uses less memory, because listing sessions no longer keeps a full copy of each running session's history. When reporting issues with /feedback, if a record is very large, the system automatically shortens it to fit and adds a note, so it no longer fails due to oversized files.

BUGFIX

Hook Context Stays in Current Conversation, Preventing Full History Reprocessing

If you typically use automation scripts to augment prompts or tool results, the scope of data injection is now more clearly defined. After a prompt or tool call, context added through hooks (small programs triggered by specific events) is now strictly confined to the conversation where that information arrived.

Adopting the sticky-note mechanism used in document review, newly added review comments are attached solely to the current folder instead of pulling out the entire historical archive to re-examine from start to finish.

After adding a new hook rule, the next model call no longer re-processes the entire conversation.
