Muse Code 1.4.17

Released: 2026-11-13

Release notes

BUGFIX

Improved Agent Blocker Reporting and Build Debugging

When development tasks run into a blocked network, a behind branch, or a form, Muse now responds in a different order. Whenever a network policy blocks a download that a step needs, it asks you right away before running other steps, instead of trying other sources or waiting until the final report to mention it. If your branch is behind and its build fails, it builds and tests on the up-to-date branch instead. If the failure output mentions a fix, it also keeps working until that fix is applied or offered to you. When interacting with browser app forms, they now return results directly from your click instead of waiting for a background step to finish.

Picture bringing documents to a copy shop and running into a paper-size restriction: instead of trying a different paper on their own or telling you only at the end, the clerk stops and asks you right away.
FEATURE

Agent Asks Before Changing Environment Settings or Background Services

Having Muse finish a small tool and install the command into your computer's path without asking is frustrating. Now, unless you explicitly asked for it, Muse stops and asks you before doing any of the following. This includes putting a newly built program on your PATH, replacing or shadowing an existing command with the same name, editing shell startup files, or installing a background service.

Think of getting a haircut: if the stylist wants to switch your shampoo or add a conditioning treatment, they always ask for your nod first rather than doing it without telling you.
BUGFIX

Browser Games Follow Your Specified Tech Stack

When you wanted to build a small browser game with a specific framework, Muse used to always make plain HTML files no matter what you asked for. Now, as long as you name the tech stack you want in your request, it implements the game using what you specified.

BUGFIX

Content Check Reports List Draft-Only Items Separately

When you ask the Agent for a check report that separates published from unpublished content, assets that only appear in drafts used to be easily mislabeled as unused or left out altogether. Now, before reporting that it is done, the Agent is prompted to rerun the check and list items used only by unpublished content under a dedicated draft-only heading, instead of calling them unused or leaving them out.

FEATURE

Long Conversations Prevent Overflow and Suggest Starting a New Session

When a chat with AI grows long and piles up history, hitting send only to get a request-too-large error is the last thing you want. Whenever a model's context window (the total amount a single conversation can hold) is known, Muse trims the requested reply length to fit the remaining room before sending your prompt, preventing common request-too-large errors in long chats. If that turn's content still exceeds the model's capacity limit, the error message now tells you directly that you can start a new session instead.

It is like packing an almost-full trunk: you first shrink the size of the box going in next, and if it still cannot fit at all, you simply switch to an empty car.
BUGFIX

Block Hidden Terminal Control Codes in /goal Summaries

When tracking tasks with /goal, model-generated text could previously change the window title, clear the screen, or move the cursor. This security issue is fixed: invisible terminal control characters are now stripped before the /goal summary prints, so model text in the summary can no longer alter the terminal title, clear the screen, or move the cursor.

Take a sticky note on a bulletin board: hidden marks on it used to trick someone into changing the board's title, but wiping those marks off first leaves it as a plain-text notice.
FEATURE

Update Before Resuming Cross-Machine Chats and Failed Workflows

When mixing older and newer versions of Muse across different devices, watch out for compatibility when resuming chats. If a newer build connected or tried to connect to another machine to run commands, an older build cannot open that chat. If you open it in an older build by ID or through the session picker, the older build may start a new local chat on its own, read the old log, and continue the work right on this computer. Because that work may have been meant for the other machine, update the app before reopening the chat; other chats are unaffected. Older app versions also cannot resume a workflow that recorded a failed status check, so you must update the app to resume it as well.

Like an old GPS reading a new route, it might reroute a local trip on its own when it cannot understand cross-region markers, so upgrading first keeps you from running in the wrong place.
BUGFIX

Fix Session Resume Failures and Picker Selection Issues

Pulling up an in-progress session to resume used to break anywhere from the picker list to loading state, and those breakpoints are now fixed. When a resume fails and returns to the session picker, the session you just tried is selected as soon as the list shows it, so pressing Enter no longer opens a different one by mistake. When a session has to continue in a new session, resuming no longer fails even if its newest checkpoint was written between turns, and the conversation content is kept. After compacting and reopening a session, saved workflows remain available to resume. When reopening with --resume, --continue, or /resume, if a subagent (a separate helper that handles subtasks) cannot have its state read, expanded history no longer shows it twice. Reopening a session no longer fails when saving setup failed on an earlier turn and the next turn reused the same rules or instructions. If a forked session ran before recording its workspace, it claims that workspace on its next resume, and the picker lists it under the current workspace instead of hiding it.

BUGFIX

Session Listings Stop Holding Logs Open and Label Side Chats

Checking your saved session list no longer locks up files while running, and how conversations relate to each other is clear at a glance. Session listings now run in two phases by default, so long lists no longer keep log files open while running; the displayed list stays the same, though old log files that have already grown very large do not shrink yet. When you run muse sessions, parked side chats are now labeled as branches of their original conversation instead of appearing beside it as unowned sessions.

An inventory clerk at a library now copies catalog entries in two passes instead of propping the archive door open and blocking the aisle the whole time, while also labeling any side volume set aside with the main series it belongs to.
FEATURE

Idle Sessions Return Memory Freed by Compaction Faster

Having several chat windows open after compacting logs and pausing the conversation used to leave your computer's memory usage stubbornly high. Previously, sessions often held onto the memory freed by compaction for several minutes; now, after sitting idle for about half a minute, they return that memory to the system.

FEATURE

Workflow token budgets fully count subtask usage

When a multi-step workflow dispatches a subtask that runs for several turns, the calculated usage used to come up short. Workflow token (a unit of text used for AI processing and billing) budgets and subtask consumption now count all stages of a subtask's work, rather than only its first turn.

BUGFIX

Fix background-task approvals and layout issues after stopping tasks

After handing work off to a background task and letting it finish or stopping it manually, on-screen controls now behave much better. Session messages sent after a background task finishes can now be approved normally. Pending approval cards also show the background task trigger separately from the sender. After stopping a task from the Tasks drawer or with /stop all, a second prompt row no longer appears under your next message.

BUGFIX

Fix queued prompts arriving empty when triggering hooks

While the previous turn is still running, you can submit your next prompt to queue it. Previously, UserPromptSubmit hooks (small programs triggered by specific events) received an empty prompt in this case. This issue is fixed, and queued prompts now pass into the hooks with their original text.

FEATURE

Disabled plugin skills stay off after updating the plugin

When you manually turn off an unused skill in a plugin, the last thing you want is for it to turn back on after an update. Even if the plugin author moves that skill's folder, a skill you disabled now stays off after you update the plugin.

BUGFIX

Reading incomplete JPEGs now reports a damaged file

If you accidentally add a half-saved JPEG image that is cut off at the end to a conversation, the app used to send that broken image straight to the model, causing the whole request to be rejected. Reading an incomplete JPEG now fails immediately with the message "the file may be damaged or invalid", instead of sending the damaged image to the model.

BUGFIX

Clearer guidance when settings.json lacks a version number

If settings.json on your computer was created by another tool, it often lacks a format version number, and opening Muse used to report only a cryptic parse error. Now when schema_version is missing, it clearly tells you to add this line to the configuration file:

{
  "schema_version": 1
}
BUGFIX

Startup blocking rules when settings.json cannot be read

If you accidentally lock down permissions on settings.json so nobody can open it, this release draws clearer lines around how startup behaves in each scenario. When muse serve hits this while reading the hooks list, it no longer reports zero hooks and instead refuses with the read error and a fix suggestion. Resuming a session with muse resume <id> or muse exec --session-id <id> also stops at startup for the same reason. A fresh muse or muse exec run keeps its existing permission-profile refusal. Commands that run no hooks continue using defaults after showing a single warning.

When a construction site's safety manual gets waterlogged and unreadable, crews that must follow the manual no longer pretend there are no restrictions and start work—they halt first and include troubleshooting steps, while tasks unrelated to the manual log a reminder and finish as usual.
BUGFIX

Sessions still open when trust.json cannot be read

When checking workspace trust through muse serve, if the file recording the trust list was damaged or blocked by permissions, opening used to fail outright. This issue is fixed: when trust.json cannot be read, the session still opens normally, with any extra workspace folders left untrusted.

FEATURE

Shell commands in the Mac sandbox can use ssh normally

When running terminal commands in an isolated environment on macOS, using the remote connection tool ssh used to get stuck unable to look up the current user name. This issue is fixed, so shell commands inside the sandbox (an isolated, secure execution environment) can look up the user name normally and ssh works just as it does outside the sandbox.

FEATURE

Mac login screen explains how to fix Keychain access issues

When starting Muse Code on a Mac over a remote SSH connection from another computer, it used to unexpectedly show a logged-out state with no explanation on screen of what went wrong. This usually happens because the Keychain cannot be used at startup. Now in this situation, the login screen explains the cause and includes the fix, reminding you to run security unlock-keychain and then restart Muse Code.

Suppose your keycard fails to open the office door: before, the reader only flashed red and treated you as absent, whereas now the screen tells you the card is demagnetized and shows which machine to use to re-encode it.
BUGFIX

Windows sandbox setup now names the step where it failed

Running muse sandbox windows setup on Windows, or letting the first launch create the sandbox automatically, can sometimes fail mid-way. Previously, the screen only reported that the setup marker was missing, leaving you with no clue what went wrong. Now the failure message points directly to the specific step that got stuck—such as a company machine or local policy refusing sign-in for the sandbox account—so you no longer have to guess the cause.

BUGFIX

Fixed "Access is denied" when attaching images in a Windows sandbox

When working in a session folder on Windows that does not allow hard links, such as inside a sandbox environment, trying to attach an image to a conversation failed with an "Access is denied" error. This issue is now fixed, so images attach normally even when the folder does not support hard links.

BUGFIX

Fixed protection and startup failures for concurrent Linux sandbox commands

Running multiple sandboxed shell commands at the same time on Linux, or hitting a scheduled system temp-file cleanup, previously caused startup failures or dropped protections. When the ~/.config directory does not exist yet and two sandboxed shell commands start together, the second command no longer fails with exit 125. The shared lock that stops sandboxed commands from undoing each other's protection no longer lives in a file that a temp cleaner can delete mid-run. If the sandbox's placeholder records are deleted by a /tmp cleaner or similar tool, protection for missing paths like ~/.config no longer disappears even when another command sharing it finishes first. When another sandboxed command starts in the same workspace, deny rules inside a missing protected folder (such as .git) are no longer lost.

BUGFIX

Fixed shell command failures in Linux worktree subdirectories

On Linux, many users create a worktree (a Git feature that lets you check out multiple parallel copies of the same project) with git worktree add. Previously, starting Muse from a subfolder inside such a directory caused every shell command to fail with a "Not a directory" error. That issue is now fixed, and shell commands run normally from subdirectories.

FEATURE

Session protocol adds subagent stop and result status notifications

For teams building custom frontend interfaces: previously, external views could not easily tell whether a background task was stopped by the user or had already handed its output back to the main thread, and this release fills in that real-time sync. The session protocol adds an experimental request that stops subagents in a session just like pressing stop in the terminal UI, letting the main agent know the user stopped them. Whenever a session reads a subagent's result, the client receives a result item with its current status—completed, failed, or cancelled—at that point, so finished subagents can be shown where the parent read the result. When a subagent starts a new attempt after an older result, that older result is marked as superseded by the newer attempt, allowing clients to read the subagent's current status directly from its control state.

BUGFIX

Fixed inaccurate save-error reporting for subagent commands

For teams integrating the session protocol or muse serve, screens and responses previously labeled any unhandled subagent command as unable to save, misleading people about the real cause. When a session log file is deleted or replaced outside Muse and the protocol refuses an interrupt, stop, close, or result-read request for a subagent, it now reports the exact reason for the refusal instead of only saying changes cannot be saved. On a muse serve session, sending a command to a subagent after resume while its history is still being rebuilt now replies that it is busy and can be retried. Even when the session cannot be saved at that moment, it no longer reports a save failure for a command that never ran.

A front-desk clerk who used to slap an "unable to save" label on any rejected filing now states plainly whether the master copy is missing or the counter is still sorting old paperwork and asks you to try again.
FEATURE

Session protocol adopts new view cursors and rebuilds old caches

For developers integrating remote clients: continuing to use reading progress or cached records left over from older versions after an upgrade could cause views to silently miss or misread events, so this release actively intercepts and refreshes them. Session-protocol view cursors are now issued in a new format; an older-format cursor is refused once with the standard reopen without a cursor guidance asking to reopen without a cursor. Any view cache saved by an older version is automatically rebuilt on first use.

At a renovated reading room, old bookmarks no longer work: the attendant asks you to reopen the book from the start and reprints the old index sheet tucked inside so you do not miss any chapters.
FEATURE

muse serve supports mixing skills and videos in a single turn

If your project integrates a muse serve client, putting a skill and multiple videos into the same turn for analysis previously had to be split apart. Now when starting a single turn, clients can send skill parts together with video parts. Each video's [Video #N] label is appended to the skill's arguments in order, working the same way as existing image labels.

FEATURE

SDKs add session event streaming and generic requests

For developers using the TypeScript and Python SDKs who want finer-grained state tracking or to call unwrapped interfaces, this release fills in several key capabilities. In the TypeScript SDK, extension hooks can now observe custom notifications during session folding as well as host-wide events. In both the TypeScript and Python SDKs, a new event-streaming interface sends the changes each incoming event makes to a session in real time, letting clients update their UI incrementally. Both SDKs also add a generic query request method for queries not yet wrapped by the client; and when the experimental API option is enabled at client startup, both regular commands and generic requests can call experimental methods.

BUGFIX

Fixed SDK host-crash error reporting and retry behavior

When developing with the TypeScript and Python SDKs, error details and retry behavior for host disconnects or busy states have been fixed in this release. When a call fails because the host process exited, the error cause now includes how it ended (exit code or signal, plus the tail of its error output). Such failures can be reported up to 2 seconds later while the SDK waits for the process to exit, and this cause does not mean the session can be resumed. If a command receives an overload or backpressure pushback marked as not retryable, the SDK no longer resubmits it automatically; without that flag, it still retries. Feedback submission calls no longer attach a command ID and no longer retry after an overload or pushback response, making each call a single submission. In SDK error messages about the Muse Code host, the compatibility link now points to the right compatibility page instead of opening a broken one.
